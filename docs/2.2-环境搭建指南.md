## 零、先搞懂 Redmine 的配置模型（不然后面全是懵的）

### 0.1 一个坑：Redmine 装完 ≠ 能测

`docker compose up -d` 只做了**建表结构**（数据库里有哪些表、哪些字段），**没有塞默认数据**。

Redmine 的默认数据（跟踪标签、问题状态、优先级……）需要单独一条命令加载。**很多 Docker 教程漏了这步**，后果是：

| 现象                    | 你以为的原因         | 真实原因                               |
| --------------------- | -------------- | ---------------------------------- |
| 管理页里「跟踪标签」是空的         | 要自己新建          | 默认数据没加载                            |
| 工作流页面点「编辑」**没反应、不跳转** | 浏览器坏了 / 选了"全部" | **没有跟踪标签和状态，那张配置表的"行"和"列"都不存在，渲染不出来** |
| 建 Issue 时「跟踪」下拉框是空的   | 权限问题           | 同上                                 |

> **本次已帮你修好**（细节见 1.2）。你之前"点编辑不跳转"就是这个原因，不是你操作错了，也不是代理问题。

### 0.2 五个概念的从属关系（这是理解 Redmine 的钥匙）

```
项目 (Project)  ←── 最外层容器，Issue / Wiki / 论坛都挂在项目下
 │
 ├── 成员 (Members)  ←── 把「用户」和「角色」绑定在一起
 │      │                 例：把 reporter1 以 Reporter 角色加进项目
 │      │
 │      └── 角色 (Role)  ←── 一篮子权限的集合：能看什么、能改什么
 │             │             例：Reporter 能"新建问题"，不能"删除问题"
 │             │
 │             └── 工作流 (Workflow) ←── 在"有权限"的基础上，再限制
 │                                        "能把问题从哪个状态改到哪个状态"
 │
 └── 问题 (Issue)  ←── 你要测的核心对象
        ├── 类型 → 跟踪标签 (Tracker)：Bug / Feature / Support
        └── 状态 (Status)：New → In Progress → Resolved → Closed …
```

**关键理解 —— 权限和工作流是两层不同的门**：

| 层 | 管什么 | 在哪个页面配 | 不配的后果 |
|---|---|---|---|
| **角色权限** | 能不能**进这道门**（能不能看 Issue、能不能改 Issue） | 管理 → 角色与权限 | 没勾"新建问题"，连 Bug 都提不了 |
| **工作流** | 进门后**能走哪条路**（New → In Progress 允许，New → Closed 不允许） | 管理 → 工作流 | 权限够了，但打开状态下拉框**一个选项都没有**，改不了状态 |

> 这两层是**与**的关系：必须「有权限」**且**「工作流允许」，操作才能成功。所以越权测试（P 组用例）和状态机测试（S 组用例）分别打的就是这两层。

### 0.3 正确的配置顺序（顺序错了要返工）

```
① 跟踪标签 / 问题状态  （先把"零件"造出来）
        ↓
② 角色与权限          （决定谁能动这些零件）
        ↓
③ 工作流              （决定状态能怎么流转 — 配置表的"行/列"就是①里的状态）
        ↓
④ 项目 + 成员         （把人放进项目，角色才有意义）
        ↓
⑤ 开始跑用例
```

**为什么工作流必须在①之后**：工作流配置表的**表头（列）就是你的「问题状态」，每一行同样是一个状态**。状态表是空的，这张表就是空的，点进去什么都没有。

> **先看懂"表头是什么"**：Redmine 的工作流页面长得像下面这样 —— **横着排（列）是"当前状态"，竖着排（行）是"想改成的新状态"**，交叉的方格打勾 = 允许这次转变。
>
> ```
>                 当前状态（列）→
>              新建    进行中   已解决   已关闭
> 新状态 新建   —       ☐        ☐       ☐
> （行） 进行中  ☑       —        ☐       ☐
>   ↓   已解决  ☐       ☑        —       ☐
> ```
>
> 上图里「进行中 ← 新建」打了勾，意思就是：**允许把状态从"新建"改成"进行中"**。
> 就是这么一张表，没有别的玄机。

## 一、环境初始化：加载默认数据

### 1.1 为什么会漏

Redmine 的官方说明里，默认数据靠这条命令加载：

```bash
rake redmine:load_default_data
```

Docker 镜像**不会自动执行它**（因为怕覆盖你已有的数据）。所以第一次部署完，必须先手动跑一次。

### 1.2 你的环境已经补好了（本次记录）

**问题现场**（我直接查了你容器里的 MySQL，不是猜的）：

| 数据表                           | 应有  |  你的实际情况   |
| ----------------------------- | :-: | :-------: |
| `trackers`（跟踪标签）              | 3 条 | **0 条** ❌ |
| `issue_statuses`（问题状态）        | 6 条 | **0 条** ❌ |
| `enumerations`（优先级/活动类型/文档分类） | 9 条 | **0 条** ❌ |
| `roles`（角色）                   | 5 条 |   5 条 ✅   |

**修复过程中踩到的两个坑**（记录在此，重建环境时会再遇到）：

**坑 1：`rake redmine:load_default_data` 报 secret_key_base 缺失**

```
ArgumentError: Missing `secret_key_base` for 'production' environment
```

原因：`docker exec` 进容器跑 rake 时，Rails 没读到密钥。解决：把你 `docker-compose.yml` 里那个 `REDMINE_SECRET_KEY_BASE` 显式传给 Rails 的标准变量名：

```bash
SECRET_KEY_BASE="$REDMINE_SECRET_KEY_BASE" RAILS_ENV=production bundle exec rake ...
```

**坑 2：官方命令拒绝执行，说「Some configuration data is already loaded.」**

这是 Redmine 源码里的一个硬性检查（`lib/redmine/default_data/loader.rb`）：

```ruby
def no_data?
  !Role.where(builtin: 0).exists? &&     # ← 没有非内置角色
    !Tracker.exists? && !IssueStatus.exists? && ...
end
```

你已经建了 Reporter / Developer / Manager 三个角色，`Role.where(builtin: 0).exists?` 就是 `true`，于是它认为"数据已加载"，**拒绝往下走** —— 但实际上跟踪标签和状态一个都没有。这是个半初始化死锁。

**解决办法**：不走它的统一入口，用 `rails runner` 只补缺失的那几张表。

### 1.3 重建环境时的完整命令（照抄）

补数据脚本已存在 `scripts/seed-default-data.rb`，重建环境后执行：

```bash
cd scripts

# 1) 拷进容器
docker cp seed-default-data.rb redmin_test-redmine-1:/tmp/seed.rb

# 2) 执行（关键是把 SECRET_KEY_BASE 显式传进去）
docker exec redmin_test-redmine-1 sh -c "cd /usr/src/redmine && export SECRET_KEY_BASE=\"$REDMINE_SECRET_KEY_BASE\" && RAILS_ENV=production bundle exec rails runner /tmp/seed.rb"
```

**期望输出**：

```
===== 补齐结果 =====
  - 问题状态 x6
  - 跟踪标签 x3
  - 项目[v1-0]关联了 3 个跟踪标签
  - 优先级 x5
  - 文档分类 x2
  - 活动类型 x2
```

### 1.4 验证命令（怎么确认真的补齐了）

```bash
docker exec redmin_test-db-1 mysql --default-character-set=utf8mb4 -uredmine -predmine123 redmine -N -B -e "select 'trackers' t, count(*) from trackers union all select 'issue_statuses', count(*) from issue_statuses union all select 'issue_priorities', count(*) from enumerations where type='IssuePriority';"
```

**期望**：`trackers 3` / `issue_statuses 6` / `issue_priorities 5`

> **为什么用命令行验证而不是看网页**：网页只能看一个页面，命令行一次能确认三张表。而且这套查询不依赖登录，随时可查。

## 二、跟踪标签（Tracker）

### 2.1 是什么

Tracker = Issue 的**类型**。同一个"新建问题"表单，选 Bug 是提缺陷，选 Feature 是提需求，选 Support 是提支持请求。**测试用例里 F1-01 ~ F1-05 就覆盖了这个字段的枚举值**。

### 2.2 你现在的值（已自动建好）

| ID | 名称 | 默认状态 | 出现在路线图 |
|:--:|------|---------|:---:|
| 1 | **Bug** | New | 否 |
| 2 | **Feature** | New | 是 |
| 3 | **Support** | New | 否 |

> **`is_in_roadmap`（出现在路线图）**：勾上表示这类 Issue 会汇总到项目的"路线图/版本"页面。Bug 和 Support 通常不进路线图，Feature 进 —— 这是 Redmine 官方默认，不用改。

### 2.3 检查 / 修改入口

浏览器打开：**管理（Administration）→ 跟踪标签（Trackers）** → `http://localhost:3000/trackers`

> **额外检查项**：新建项目时默认启用哪些 tracker，由 `管理 → 设置 → 项目` 里的「默认启用的跟踪标签」控制。你已经有一个项目（identifier = `v1-0`），我脚本里已把 3 个 tracker 都挂到它上面了 —— 否则你在项目里点"新建问题"时会发现**跟踪下拉框是空的**（这是常见坑，见第八章）。

## 三、问题状态（Issue status）

### 3.1 是什么

Issue 当前处在哪个阶段。这是**状态机测试的"状态集合"**（用例 S 组全靠它）。

### 3.2 你现在的值

| ID | 名称 | 是否"已关闭" | 位置 |
|:--:|------|:---:|:--:|
| 1 | **New**（新建） | 否 | 1 |
| 2 | **In Progress**（进行中） | 否 | 2 |
| 3 | **Resolved**（已解决） | 否 | 3 |
| 4 | **Feedback**（反馈） | 否 | 4 |
| 5 | **Closed**（已关闭） | **是** | 5 |
| 6 | **Rejected**（已拒绝） | **是** | 6 |

### 3.3 关键概念：`is_closed`（「已关闭」标记）

Redmine 里"已关闭"**不是一个状态名，而是一个布尔标记**。被标记的状态（Closed / Rejected）会：

- 在 Issue 列表的"打开/已关闭"过滤器里归到"已关闭"
- 默认不出现在待办统计里
- 只有带 `:view_issues` 权限的角色还能看到（默认列表会过滤掉）

> **测试时要注意**：S-08「New → Rejected」虽然是"拒绝"，但 Rejected 被标记为已关闭 —— 所以这条转移成功后，这条 Issue 在默认列表里就"消失"了。这是设计如此，不是 bug。

### 3.4 检查入口

**管理 → 问题状态** → `http://localhost:3000/issue_statuses`

### 4.2 三组"只差几个字、含义完全不同"的权限（易混点，必记）

Redmine 的界面中文名长得很像，**操作时很容易搞反**。下面这几组是按危险程度排的：

| 权限 A（界面名 / 标识） | 权限 B（界面名 / 标识） | 区别 | 危险度 |
|---|---|---|---|
| **更新问题** `edit_issues` | **更新自己的问题** `edit_own_issues` | A = 能改**任何人**的 | ⚠️ 给错就直接毁掉越权测试 |
| **编辑注释** `edit_issue_notes` | **编辑自己的注释** `edit_own_issue_notes` | A = 能改**任何人**写的注释 | ⚠️ 高 |
| **编辑耗时** `edit_time_entries` | **编辑自己的耗时** `edit_own_time_entries` | A = 能改**任何人**登记的工时 | 中 |
| **管理问题关联** `manage_issue_relations` | **管理相关问题** `manage_related_issues` | A 在「问题跟踪」区块，管 **Issue 之间**的关联；B 在「版本库」区块，管**代码提交与 Issue**的关联 | 低（易混但不危险） |
| **管理版本库** `manage_repository` | **浏览版本库** `browse_repository` | A = 能**改仓库配置**；B = 只能**看代码** | ⚠️ 高 |
| **查看私有注解** `view_private_notes` | **设置注释为私有** `set_notes_private` | A = 能**看到**别人的私有注释；B = 能**把自己的**注释设为私有 | 中 |

> **⚠️ 再更正一处**：我前面说"`manage_issue_relations` 不在'问题跟踪'区块，而在版本库区块，叫'相关问题管理'"—— **这是错的**。这是**两个不同的权限**，`manage_issue_relations` 就在「问题跟踪」区块里，界面名叫「管理问题关联」。你按那个错误提示去找会找不到。

**记法**：中文界面里凡是带「**自己的**」三个字的，都是"仅限自己创建的"；不带的就是"任何人的"。

### 4.4 一键校正脚本（想重来时用）

权限是**手工勾选最容易出错**的地方（本次就错了两处）。校验脚本已落地：


## 五、工作流（Workflow）—— 本章是重点

### 5.1 为什么必须配（不配 / 配错会怎样）

**不配**：任何角色打开 Issue 点「更新」，状态下拉框里**一个选项都没有**。所有 S 组用例（10 条状态机用例）全部跑不起来。

**用默认值**：**S-05 会失败**。因为 Redmine 的默认工作流里，Developer 是**允许**从「新建」直接跳到「已关闭」的。

#### 我直接把 Redmine 官方默认工作流的源码读出来了

**来源**：`/usr/src/redmine/lib/redmine/default_data/loader.rb`（Redmine 6 官方镜像里的默认数据加载器）。

```ruby
# ① Manager：所有状态 → 所有状态（除自身到自身）
Tracker.all.each do |t|
  IssueStatus.all.each do |os|
    IssueStatus.all.each do |ns|
      unless os == ns
        WorkflowTransition.create!(..., :role_id => manager.id,
                                        :old_status_id => os.id,
                                        :new_status_id => ns.id)
      end
    end
  end
end

# ② Developer：[新建, 进行中, 已解决, 反馈] → [进行中, 已解决, 反馈, 已关闭]
Tracker.all.each do |t|
  [new, in_progress, resolved, feedback].each do |os|
    [in_progress, resolved, feedback, closed].each do |ns|
      unless os == ns
        WorkflowTransition.create!(..., :role_id => developer.id, ...)
      end
    end
  end
end

# ③ Reporter：[新建, 进行中, 已解决, 反馈] → [已关闭]  +  已解决 → 反馈
Tracker.all.each do |t|
  [new, in_progress, resolved, feedback].each do |os|
    [closed].each do |ns|
      unless os == ns
        WorkflowTransition.create!(..., :role_id => reporter.id, ...)
      end
    end
  end
  WorkflowTransition.create!(..., :role_id => reporter.id,
                                  :old_status_id => resolved.id,
                                  :new_status_id => feedback.id)
end
```

**翻译成人话**：

| 角色 | 官方默认允许什么 | 每 tracker 条数 |
|---|---|:---:|
| **Manager** | 任意状态 → 任意状态（跳步、回退、重开，全允许） | 30 |
| **Developer** | 新建/进行中/已解决/反馈 之间互相流转，**并且能直接 → 已关闭** | 12 |
| **Reporter** | 新建/进行中/已解决/反馈 **→ 已关闭**，外加 已解决 → 反馈 | 5 |

#### 三个关键结论（这就是"为什么必须定制"的答案）

| # | 结论 | 说明 |
|:--:|---|---|
| **1** | **官方默认是"放宽"的，不是"收紧"的** | Developer 在默认配置下**能从「新建」直接跳到「已关闭」**。而用例 S-05 要求这条转移非法 —— **不收紧就永远测不出来** |
| **2** | **官方默认里 Reporter 是有工作流的** | 官方给了他 5 条规则（含 `× → 已关闭`）。所以你截图里"没有为此角色定义工作流程"**不是说官方没配** —— 根因是部署时默认数据就没加载成功（见第一章），补数据时又只补了状态和跟踪标签，**工作流没一起补** |
| **3** | **但官方给的 Reporter 权限里没有 `edit_own_issues`** | 官方没给他"更新自己的问题"权限 —— **没这个权限，那 5 条工作流规则等于摆设**（工作流是"路"，权限是"门"，门没开，路修了也走不了）。官方设计里 Reporter 提完单就退场 |

> **⚠️ 所以本项目做了一个有意的偏离**：给 Reporter 加上 `edit_own_issues`，再把他的工作流从官方的"× → 已关闭"收紧成"新建 ↔ 反馈"。
>
> 这样 Reporter 就成了一个**"受限但可用"**的角色 —— 三种角色在同一个状态下能看到 1 / 2 / 5 个选项，权限梯度一目了然。**这个设计过程本身就值得记录**：
>
> > "Redmine 默认工作流是放宽的（Developer 能跳步关闭），我要测非法转移就必须先收紧；同时默认给 Reporter 的规则因为缺少 `edit_own_issues` 权限而实际无效，我把它改成了受限的合法流转，用来验证权限和工作的双重约束。"

> **一句话记住"为什么工作流不是多此一举"**：**默认值服务于"用起来方便"，而测试需要的是"规则明确"。** 把业务规则转成测试约束，就是工作流配置这件事的本质。

### 5.2 工作流配置表怎么读（先看懂界面）

**入口**：管理 → 工作流 → `http://localhost:3000/workflows`

页面顶部有**两个下拉框**（**角色** + **跟踪标签**），选好后点右边的「**编辑**」按钮，下方才会展开那张勾选表。

> **为什么要点"编辑"才出来**：Redmine 把这张表设计成"按角色+跟踪标签分别配置"。你想配"开发者在 Bug 类型下的流转"，就得先在下拉框里选 `Developer` + `Bug`，再点编辑。

**表格的读法**（这是最容易搞反的地方）：

```
                  当前状态 (Current status)  →
              ┌────────┬──────────────┬──────────┬──────────┐
              │  New   │ In Progress  │ Resolved │  Closed  │
  新状态  ┌───┼────────┼──────────────┼──────────┼──────────┤
 (New    │New│   —    │      ☐       │    ☐     │    ☐     │
  status) │  │        │              │          │          │
    ↓     │In│   ☑    │      —       │    ☐     │    ☐     │
          │Pr│        │              │          │          │
          └──┴────────┴──────────────┴──────────┴──────────┘
                  ↑ 勾这里 = 允许 New → In Progress
```

**一句话记法**：**勾哪个格子 = 允许"从列状态 → 到行状态"**。对角线（自己到自己）是灰色不可勾的。

#### ⚠️ 顺便解释你截图里那个黄色警告

你在「管理 → 角色与权限」页面看到 **Reporter** 那行写着：

```
⚠ 没有为此角色定义工作流程(编辑)
```

**这个警告的字面意思**：这个角色在那张工作流配置表里，**一条勾都没有**（空格子全空）。

**它是不是错误？** 取决于你的设计：

| 情况 | 说明 |
|---|---|
| **你确实想让这个角色完全不能改状态** | 那这个警告就是**符合预期的**，忽略它 |
| **你想让这个角色能走一部分流转** | 那就是**没配完**，需要去工作流页面补勾 |

**本项目的实际情况**：这个警告是**真实缺口**，已经修好了 —— 之前 Reporter 是 0 条规则，现在补了 2 条（见 5.3 的表 A）。

> **顺带说明**：Redmine **全新安装、还没配过任何工作流时，所有角色都会显示这个警告**。这就是它的含义 —— "这个角色的流程还没配"。不是系统坏了，也不是你操作错了。
>
> 判断方法：点这个警告链接，看那张表是不是空格子。是 → 就是没配。

### 5.3 本项目的标准配置（照这个勾）

状态顺序：**New(新建) / In Progress(进行中) / Resolved(已解决) / Feedback(反馈) / Closed(已关闭) / Rejected(已拒绝)**

**跟踪标签那一栏选「全部」（All）** —— 一次把 Bug/Feature/Support 三个都配好，避免只配了 Bug 之后，建 Feature 类型 Issue 时又改不了状态。

> 下面三张表分别对应三个角色。**每张表只勾一次，但因为它对 Bug/Feature/Support 三个跟踪标签都生效，所以数据库里的规则条数 = 勾选格数 × 3。**

#### 表 A：Reporter（报告者）—— 只勾 2 格

**先对比官方默认**（见 5.1 的源码）：官方给 Reporter 的是「新建/进行中/已解决/反馈 → **已关闭**」共 5 条 —— 也就是**官方允许报告者自己关掉 Issue**。

本项目**有意收紧成下面这 2 格**，理由：报告者提完 Issue 后就该退场，只保留"配合补充信息"的能力。

| 新状态 ↓ \ 当前状态 → | New | In Progress | Resolved | Feedback | Closed | Rejected |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| **New** | — | ☐ | ☐ | **☑** | ☐ | ☐ |
| **In Progress** | ☐ | — | ☐ | ☐ | ☐ | ☐ |
| **Resolved** | ☐ | ☐ | — | ☐ | ☐ | ☐ |
| **Feedback** | **☑** | ☐ | ☐ | — | ☐ | ☐ |
| **Closed** | ☐ | ☐ | ☐ | ☐ | — | ☐ |
| **Rejected** | ☐ | ☐ | ☐ | ☐ | ☐ | — |

**每条勾选的含义**：

| 勾选（行/列） | 含义 | 对应用例 |
|---|---|---|
| Feedback ← New | 报告者发现信息不足，退回要求补充 | S-10（受限但合法的流转） |
| New ← Feedback | 信息补齐了，重新提交处理 | S-10 |

**故意不勾的关键两处**：

| 不勾 | 为什么 |
|---|---|
| **Closed ← New**（以及任何 → Closed） | **报告者无权关闭 Issue** —— 关闭权在管理者手上，这是权限分离设计。对应用例 **S-10 / P-02** |
| **In Progress ← New** | 报告者不能"认领开工"，那是开发者的动作 |

> **要理解的设计意图**：报告者能做的**只有"在新建和反馈之间来回"**这一件小事。这恰好演示了权限的**颗粒度** —— 不是"有权限 / 没权限"那么简单，而是**同一张表上，不同角色勾的格子数完全不同**。
>
> **对比一下**：报告者 2 格，开发者 11 格，管理者 30 格。这就是三个角色的权力梯度。

#### 表 B：Developer（开发者）—— 勾 11 格

| 新状态 ↓ \ 当前状态 → | New | In Progress | Resolved | Feedback | Closed | Rejected |
|---|:---:|:---:|:---:|:---:|:---:|:---:|
| **New** | — | ☐ | ☐ | ☐ | ☐ | ☐ |
| **In Progress** | **☑** | — | **☑** | **☑** | ☐ | **☑** |
| **Resolved** | ☐ | **☑** | — | **☑** | ☐ | ☐ |
| **Feedback** | ☐ | **☑** | **☑** | — | ☐ | ☐ |
| **Closed** | ☐ | ☐ | ☐ | ☐ | — | ☐ |
| **Rejected** | **☑** | **☑** | ☐ | **☑** | ☐ | — |

**每一条勾选对应哪个用例**（工作流设计的依据）：

| 勾选（行/列）                           | 含义        | 对应用例        |
| --------------------------------- | --------- | ----------- |
| In Progress ← New                 | 认领开工      | **S-01** 合法 |
| Resolved ← In Progress            | 修完了       | **S-02** 合法 |
| In Progress ← Resolved            | 打回重做      | **S-04** 合法 |
| Rejected ← New                    | 直接判定为无效   | **S-08** 合法 |
| In Progress ← Rejected            | 被拒后重新开工   | **S-09** 合法 |
| In Progress ← Feedback            | 反馈完继续做    | 补充覆盖        |
| Resolved ← Feedback               | 反馈结论转为已解决 | 补充覆盖        |
| Feedback ← In Progress            | 需要更多信息    | 补充覆盖        |
| Rejected ← In Progress / Feedback | 处理中发现无效   | 补充覆盖        |

**故意不勾的（关键！）**：

| 不勾（行/列） | 为什么 | 对应用例 |
|---|---|---|
| **Closed ← New** | 不允许跳步关闭 | **S-05** 预期「下拉框无此选项」 |
| **任意 ← Closed** | Closed 是终态，不能改出去 | **S-06** 预期非法 |
| **Closed ← Resolved** | **关闭权限留给 Manager** | **S-03** 要由 Manager 完成 |
| New ← In Progress | 不允许随便退回新建 | **S-07**（见 5.6 的说明）|

#### 表 C：Manager（管理者）—— 勾 30 格（除对角线外全勾）

6 个状态 × 6 个状态，去掉对角线（自身到自身不可勾），**30 个格子全勾**。

这样 Manager 能：跳步关闭（New → Closed）、重新打开已关闭的 Issue（Closed → New）、批准解决（Resolved → Closed，即 **S-03**）。

> **为什么管理者要全通**：他是项目负责人，需要能处理任何异常情况 —— 包括"这条 Issue 报错了，直接关掉"这种非常规操作。**这恰好和开发者的收紧形成对比**，是权限梯度里的最高层。

## 八、常见坑与报错排查

| 现象 | 真实原因 | 解决 |
|------|---------|------|
| **工作流页面点「编辑」不跳转/白屏** | 跟踪标签或问题状态表是空的，表没东西可渲染 | 跑第一章的补数据命令；确认 `trackers=3`、`issue_statuses=6` |
| **角色页显示"没有为此角色定义工作流程"** | 该角色在工作流里一条勾都没有 | 见 5.2 的说明。想让它能走流程就去工作流页配；确实不想配就忽略 |
| **状态下拉框里一个选项都没有** | 该角色在该 tracker 下没配工作流 | 进 管理→工作流，选对「角色 + 跟踪标签」，按 5.3 的表勾选并保存 |
| **新建 Issue 时「跟踪」下拉是空的** | 项目没有关联任何 tracker | 项目→设置→**信息/模块**里检查；或用 `seed-default-data.rb` 重跑（脚本会自动关联） |
| **登录后看不到任何项目** | 账号不是项目成员 | 第六章，把账号加进项目 |
| **Reporter 点「更新」只有「反馈」一个选项** | 这是**预期行为**（设计如此，见 5.3 表 A） | 不是 bug，记录实测结果到用例表 |
| **点「更新」时提示"没有权限"** | 角色缺 `edit_issues` / `edit_own_issues` | 对应用例：P-01/P-02 属预期；若 Developer 也报错则回第四章补权限 |
| **改了工作流但没生效** | 浏览器缓存了旧表单 / 保存未成功 | `Ctrl + F5` 强刷；重新进 /workflows 看勾选是否还在 |
| **工作流保存时报错** | 跟踪标签选了具体某个但该 tracker 已禁用 | 换「全部」，或先在 管理→跟踪标签 确认启用 |
| **`rake` 命令报 secret_key_base 缺失** | exec 没传密钥 | 用 1.3 的完整命令（带 `SECRET_KEY_BASE="$REDMINE_SECRET_KEY_BASE"`） |
| **`load_default_data` 说 already loaded 但数据是空的** | Redmine 的 `no_data?` 检查被已有角色触发 | 用 `seed-default-data.rb` 绕过（1.3） |
| **四个账号全部提示「无效的用户名或密码」** | 有脚本用 `u.password = xxx; u.save` 改密码，但 `save` **静默失败**（返回 false 不抛异常），密码字段一个字节没改 | 跑 `reset-passwords.cmd`（见下方 8.1）。**别自己写改密码的脚本**，密码字段的写入必须当场校验 |

### 8.1 账号登不上去的排查套路（红字案例）

**症状**：`admin` / `reporter1` / `developer1` / `manager1` 四个账号全部报「无效的用户名或密码」，明明没改过密码。

**第一步：区分「密码错了」还是「账号被禁了」**

```bash
docker exec redmin_test-db-1 mysql --default-character-set=utf8mb4 -uredmine -predmine123 redmine -e \
"select id, login, status, passwd_changed_on, updated_on from users order by id"
```

- `status=1` 是正常（可登录），`status=3` 是被锁定
- **重点看 `passwd_changed_on`**：如果它还是很久以前的时间，说明密码**从来没被成功改过**

**第二步：直接问 Redmine 密码对不对**（这是最权威的判定，不看数据库里的哈希）

```bash
docker exec redmin_test-redmine-1 sh -c 'cd /usr/src/redmine && export SECRET_KEY_BASE="$REDMINE_SECRET_KEY_BASE" && RAILS_ENV=production bundle exec rails runner "
u = User.find_by(login: \"admin\")
puts u.check_password?(\"Test@1234\")
"'
```

`false` = 密码不是这个；`true` = 密码对，问题在别处（账号被禁、浏览器缓存）。

> **为什么要用 `check_password?` 而不是看数据库**：Redmine 的密码存成 `SHA1(salt + SHA1(密码))`（源码 `app/models/user.rb` 的 `salt_password`），哈希是**不可逆**的，肉眼看不出来。而 Rails 控制台能直接问模型。

**第三步：修复**

```cmd
cd scripts
reset-passwords.cmd
```

这个脚本会重置 4 个账号，**并且每个账号都做 `reload` + `check_password?` 二次校验**，任何一个没生效就明确报错退出——不会像手工脚本那样"看着跑完了其实没改"。

**为什么会踩这个坑**：

> Redmine 的 `User#save` 在校验不通过时**只返回 false，不抛异常**。如果脚本写成 `u.password = xxx; u.save` 而不检查返回值、不校验 `errors`，就会**静默失败**——密码一个字节都不改，但脚本输出"完成"。所以改完之后必须 `reload` 再 `check_password?` 验证一遍。

**同一个坑的两种表现**：写脚本的人往往会补一个"修复脚本"（重置密码），但**那个修复脚本犯的是同一个错**（还是 `save` 不检查返回值），所以修不好。**判断一个改密码的脚本能不能用，就看它有没有回读校验。**
