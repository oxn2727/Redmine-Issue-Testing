# 被测系统简介：Redmine

> **这是整套资料的第一篇，而且必须最先读。**
>
> 它解决一个最根本的问题：**你要测的这个东西，到底是干什么的？**
>
> 如果跳过这篇直接去看"配权限、配工作流、跑用例"，你会一直卡在"这词什么意思、那步为什么要做"上 —— 因为**所有操作都是业务需求的实现**，不懂业务就只能背步骤，也说不出"这个系统到底在干嘛"。
>
> **读法**：第一、二章建立整体认知（它是什么、业务怎么跑）；第三章是功能模块全景（有哪些模块、各自干嘛）；第四章是**术语词典**（看别的文档卡住了就回来查）；第五章是界面地图（点哪里有什么）；第六章讲我们为什么专挑 Issue 模块；第七章是整套文档的阅读顺序。

## 第一章 Redmine 是什么

> **〔已知 · 可跳〕** 缺陷跟踪系统对你是常识 —— "谁都能提单、有人修、修完关掉、全程留痕"。这章不解释业务，只做一件事：**把 Redmine 怎么称呼这些角色和动作对上号**。扫一遍，重点看 **1.4 三种角色**。

### 1.1 一句话定义

**Redmine 是一个开源的「项目管理 + 问题跟踪」Web 系统**。用 Ruby on Rails 写的，2006 年发布，到今天还有大量公司在用。

它最核心的用途是：**把团队里"发现了什么问题、谁负责、处理到哪一步了、解决了没有"这件事，从口头/微信里搬到系统里，变得可记录、可查询、可追溯。**

**"问题"在 Redmine 里有个专门的词，叫 Issue（问题/工单）** —— 这是整个系统的核心对象，后面所有概念都是围着它展开的。

### 1.2 它到底解决什么现实问题

先看一个真实场景。假设一个 5 人小团队在做一个后台管理系统，开发过程中必然出现这些事：

| 现实里发生的事            | 没有 Redmine 会怎样                  |
| ------------------ | ------------------------------- |
| 测试发现"密码输错 3 次不锁账号" | 得跑去跟开发说，或者微信发一句 —— **事后没有任何记录** |
| 开发说"等我这波忙完再改"      | 一周后没人记得这件事 —— **漏改**            |
| 项目经理想知道进度          | 只能一个个问 —— **无法给出可靠进度**          |
| 客户追问"我提的问题怎么还没修"   | 翻聊天记录 —— **扯皮**                 |
| 三个月后这条 bug 又出现了    | 找不到当初怎么修的 —— **重复踩坑**           |

微信群 + 口头的模式，在这些问题上必然失控。所以团队需要一个**统一的、带状态流转、带责任人、带时间记录的"问题台账"**。

**Redmine 就是这个台账。** 同类产品还有 **Jira**（最主流，商业）、**禅道**（国内常用）、**Bugzilla**（老牌）、**GitLab Issues / GitHub Issues**（代码托管平台自带）。它们解决的是同一类问题，都是**缺陷 / 项目管理工具**。

### 1.3 它的核心业务闭环

Redmine 的全部价值，可以浓缩成一条闭环：

```
有人发现问题
    ↓ ① 记录下来          → 新建 Issue，写清现象和复现步骤
    ↓ ② 指派责任人        → 这条 Issue 归谁处理
    ↓ ③ 处理过程留痕      → 改状态 + 写说明，每步都有作者和时间
    ↓ ④ 验证结果          → 修好了没？验证通过才能关闭
    ↓ ⑤ 关闭 + 全程可查   → 谁在什么时候做了什么，永久可查
```

**记住这五个环节。** 后面第三章讲的所有模块、第四章的所有术语，都是为这五个环节服务的。

### 1.4 系统里有哪几种人（角色）

真实公司里，一个团队在 Redmine 里的分工是固定的。Redmine 内置了三套角色：

| 角色名（界面显示）    | 英文                     | 对应真实岗位               | 在系统里主要干什么       |
| ------------ | ---------------------- | -------------------- | --------------- |
| **报告者**      | Reporter               | 测试人员 / 客服 / 任何发现问题的人 | 提 Issue、补充信息    |
| **开发者**      | Developer              | 程序员                  | 认领、改状态、写处理说明    |
| **管理者**      | Manager                | 项目经理 / 测试主管          | 分派、审核关闭、管成员、配权限 |
| **非成员 / 匿名** | Non member / Anonymous | 未登录访客、不在项目里的人        | 权限最低，通常只能看公开内容  |

> **这三个角色是 Redmine 自带预置的**，不是我给你造的。你部署完就有这五个角色（另外两个是"非成员"和"匿名"，属于内置角色 `builtin=1`，不能删）。
>
> 预置的**权限**也是官方调好的（比如 Reporter 默认不能删 Issue）。你要做的只是**把它们加进你的项目**。

### 1.5 为什么拿它当测试对象（选型理由）

| 维度         | Redmine 的情况                                         |
| ---------- | --------------------------------------------------- |
| **真实性**    | 2006 年至今的老牌开源项目，大量企业正在用，不是培训班造出来的演示 demo            |
| **业务流清晰**  | 一条 Issue 有明确的阶段流转（新建→进行中→已解决→已关闭），**状态机测试有天然抓手**    |
| **功能面广**   | 项目 / 问题 / 版本 / Wiki / 论坛 / 权限 / 搜索 / 工时，模块多到够写好几种用例 |
| **自带接口**   | 自带 REST API（用 API Key 认证），**接口测试能真做**，不用自己搭后端       |
| **可本地部署**  | Docker 一条命令起，**性能测试（JMeter 压测）能真实落地**，不用买服务器        |
| **元层面的巧合** | 它本身就是缺陷跟踪系统，**拿它测它**，正好证明你懂缺陷管理流程                   |

## 第二章 一条 Issue 的完整旅程（业务主线）

> **〔流程已知 · 术语要看〕** 这章的流程 —— 提单 → 认领 → 修复 → 打回 → 关闭 —— 是**任何缺陷管理系统都一样**的，你不会陌生，流程叙述可以跳着扫。
>
> **这一章对你的价值在"术语落位"**：每个动作在 Redmine 里叫什么名字。所以只精读两类东西 —— 每步下面「**这里发生的事**」那个引用块，和末尾的 **2.7 对照表**。本文档要你记的术语，全在这两处出现过。

### 2.1 场景设定

**背景**：某公司在做一个电商后台管理系统。团队 4 个人：

| 人   | Redmine 账号   | 角色                 |
| --- | ------------ | ------------------ |
| 小陈  | `reporter1`  | **报告者**（测试岗）       |
| 小李  | `developer1` | **开发者**            |
| 老王  | `manager1`   | **管理者**（项目经理）      |
| —   | `admin`      | 系统管理员（管整个 Redmine） |

**现在发生的事**：小陈在测「用户登录」功能时，发现一个 bug：**连续输错 3 次密码，账号没有被锁定。**

### 2.2 第一步：报告者提 Issue

小陈登录 Redmine → 进入项目「电商后台」→ 点「**新建问题**」，填这张表单：

| 字段       | 填什么                | 这个字段的作用                  |
| -------- | ------------------ | ------------------------ |
| **跟踪标签** | `Bug`              | 说明这条是"缺陷"（而不是"新需求"或"求助"） |
| **主题**   | 密码连续输错 3 次，账号未锁定   | 一句话说清现象，列表里就显示这行         |
| **描述**   | 复现步骤 123 + 预期/实际结果 | 详细信息                     |
| **优先级**  | `高`                | 影响范围大，要优先处理              |
| **指派给**  | 小李                 | 直接指定责任人                  |
| **目标版本** | `V1.1`             | 说明"这个版本发布前要修完"           |
| **预估工时** | `2` 小时             | 排期用                      |

点「**创建**」后 —— **系统自动生成编号 `#12`**，状态默认是「**新建**」。

> **这里发生的事**：小陈干完了他的活。这条 Issue 现在躺在系统里，等着小李。
> 小陈的账户**没有"改状态到进行中"的能力** —— 因为工作流规定报告者不能认领开工（第四章会细讲）。

### 2.3 第二步：开发者认领

小李登录 → 首页「**指派给我的问题**」里看到 #12 → 点进去看明白 → 点「**更新**」，做两件事：

1. 状态下拉框选「**进行中**」 —— 表示"我认领了，正在做"
2. 写一条说明：「已定位，是登录失败计数没做持久化」

保存。

> **这里发生的事**：Issue 状态从「新建」变成「进行中」。
> **小陈和小李都会收到邮件通知**（如果配了邮件服务器）—— 这就是"可追溯"的一部分。

### 2.4 第三步：开发者修复 → 标记已解决

小李改完代码、提交、部署到测试环境。回到 #12，再点「更新」：

1. 状态改成「**已解决**」
2. 说明写：「已修复，见 commit a1b2c3」

保存。

### 2.5 第四步：测试回归 —— 发现没修好（打回）

小陈收到通知，去验证。他重新测，发现：**问题还在**，只是从"3 次不锁"变成了"4 次才锁"。

小陈在 #12 里：

1. 状态改成「**反馈**」 —— 意思是"还需要更多处理，请再看"
2. 加一条注释，贴截图，写：「仍有问题，输入 4 次才锁定」

保存。

**这就是"打回"**。小李看到通知，点「更新」，状态选「**进行中**」（从"反馈"重新开工），再去改。

> **这里发生的事**：这条 Issue 走了一条真实工作中极常见的路径：**已解决 → 反馈 → 进行中**。
> 这条路径能不能走通，**完全由"工作流"决定**。如果工作流里没勾这条，小陈点开状态下拉框会**找不到「反馈」这个选项** —— 他就只能干瞪眼。
>
> 所以"工作流"不是可有可无的配置，它**直接决定业务能不能跑通**。这也是为什么它是测试的重点对象。

### 2.6 第五步：修复通过 → 关闭

小李这次真的修好了 → 状态改成「已解决」→ 小陈回归验证**通过**。

但小陈**没有"关闭"的权限**（他的下拉框里根本没有"已关闭"这个选项）。关闭由老王执行：

老王登录 → 打开 #12 → 状态改成「**已关闭**」→ 保存。

> **为什么测试不能自己关 bug**：这是**权限分离**的设计。如果提 bug 的人能自己关，就会出现"没修好也被关掉"的情况。所以关闭权给到管理者。
>
> **这条规则正是你的用例 S-03 要验证的。**

### 2.7 这条旅程用到了什么（对照表）

| 步骤          | 用到的概念                     | 它在哪配                      |
| ----------- | ------------------------- | ------------------------- |
| 提 Issue     | 项目、跟踪标签、主题、描述、优先级、目标版本、指派 | 跟踪标签/优先级在**管理后台**，项目在项目设置 |
| 状态自动是「新建」   | 问题状态、默认状态                 | 管理 → 问题状态                 |
| 小陈不能认领      | **角色权限** + **工作流**        | 管理 → 角色与权限 / 管理 → 工作流     |
| 小李能认领、能标已解决 | 工作流                       | 管理 → 工作流                  |
| 小陈能"反馈"     | 工作流（报告者的受限权限）             | 管理 → 工作流                  |
| 小陈不能关闭      | 工作流（没有 Closed 去向）         | 管理 → 工作流                  |
| 老王能关闭       | 工作流（Manager 全通）           | 管理 → 工作流                  |
| 全程可查        | 变更历史、注释、邮件通知              | 系统自带                      |

**这就是为什么你环境搭好后必须配那五道东西** —— 不配，这条旅程在第 2.3 步就断了（下拉框没选项）。

## 第三章 功能模块全景（有哪些模块、各自干什么）

> Redmine 的模块分两层：**项目级模块**（每个项目可以单独开关）和**管理后台**（全局配置，对所有项目生效）。分开理解，不然会很乱。

### 3.1 项目级模块总览

每个项目里有这些模块，**项目管理员可以按需启用/禁用**（有些团队只开"问题 + Wiki"）：

| 模块       | 英文              | 干什么用                            | 谁用    | 和 Issue 的关系      |
| -------- | --------------- | ------------------------------- | ----- | ---------------- |
| **问题跟踪** | Issue tracking  | 提 Issue、改状态、指派、过滤、批量操作          | 全员    | **本体**           |
| **时间跟踪** | Time tracking   | 记录每条 Issue 上花了多少工时              | 开发/PM | 挂在 Issue 上       |
| **版本**   | Versions        | 划里程碑（V1.1 / V2.0），Issue 可归到某个版本 | PM    | Issue 的一个字段      |
| **路线图**  | Roadmap         | 按版本汇总"这个版本要修完哪些 Issue"、完成度百分比   | PM/客户 | 版本的汇总视图          |
| **甘特图**  | Gantt           | 时间轴视图，展示 Issue/版本的起止与依赖         | PM    | Issue 时间的可视化     |
| **日历**   | Calendar        | 按日期展示 Issue                     | 全员    | Issue 时间的可视化     |
| **新闻**   | News            | 项目公告（如"V1.0 发布说明"）              | 全员    | 独立模块             |
| **文档**   | Documents       | 放需求文档、设计文档、测试报告                 | 全员    | 独立模块             |
| **文件**   | Files           | 上传任意文件供下载                       | 全员    | 独立模块             |
| **Wiki** | Wiki            | 项目知识库，可写规范、流程、FAQ               | 全员    | 独立模块             |
| **论坛**   | Forums / Boards | 项目内讨论区，按主题发帖                    | 全员    | 独立模块             |
| **版本库**  | Repository      | 关联 Git/SVN，浏览代码提交记录             | 开发    | Issue 可关联 commit |

> **你注意一下这个结构**：除了"问题跟踪"本体，其他模块**几乎都是围着 Issue 转的** —— 版本是 Issue 的字段、时间跟踪挂在 Issue 上、甘特图和日历是 Issue 的不同呈现方式。
>
> 所以业界说"**Redmine 的本质就是 Issue 管理系统**，其他都是配套"。这也是我们选 Issue 模块深测的理由。

### 3.2 管理后台（全局配置）

管理后台是 `admin` 才能进的区域，管的是**全系统规则**，页面地址都是 `/xxx` 开头的（如 `/roles`、`/trackers`）。**你环境配置的绝大部分工作都在这里**：

| 菜单（中文界面）  | 英文                    | 干什么用                                     | 为什么测试要用到它             |
| --------- | --------------------- | ---------------------------------------- | --------------------- |
| **用户**    | Users                 | 建账号、改密码、启停用户                             | 要建 3 个测试账号            |
| **组**     | Groups                | 把一批用户打包成组，方便批量授权                         | 本次不用                  |
| **角色与权限** | Roles and permissions | **定义"一类人能做什么"**（一篮子权限的集合）                | 越权测试的前提               |
| **跟踪标签**  | Trackers              | 定义 Issue 的**类型**：Bug / Feature / Support | 用例 F1-01 ~ F1-05 覆盖它的枚举值           |
| **问题状态**  | Issue statuses        | 定义 Issue 的**阶段**：新建/进行中/已解决/已关闭/已拒绝      | 状态机测试的"状态集合"          |
| **工作流**   | Workflow              | **定义"什么角色能把状态从哪改到哪"**                    | 状态机测试的前提              |
| **枚举值**   | Enumerations          | 定义下拉选项：问题优先级、活动类型、文档分类                   | 用例 F1-01 ~ F1-05 覆盖优先级 5 个取值         |
| **问题类别**  | Issue categories      | （项目级）给 Issue 归类，如"前端/后端/数据库"             | 用例 F3 过滤用             |
| **设置**    | Settings              | 显示、认证、邮件、API、版本库等全局开关                    | API 测试要开"启用 REST API" |
| **插件**    | Plugins               | 装第三方扩展功能                                 | 本次不测                  |
| **信息**    | Information           | 看版本号、数据库版本、环境信息                          | 写测试环境描述时用             |

> **注意区分"管理后台"和"项目设置"**：管理后台管的是**全系统**（所有项目共用同一套跟踪标签、同一套工作流）；项目设置管的是**这一个项目**（这个项目启用哪些模块、有哪些成员、有哪些版本）。两者容易混，看地址栏能分清：`/roles` 是管理后台，`/projects/v1-0/settings/members` 是项目设置。

### 3.3 Issue 模块内部的功能点（你要测的东西）

这就是你要深测的模块，把它的功能点摊开：

| 功能点          | 具体能做什么                                                                 |
| ------------ | ---------------------------------------------------------------------- |
| **创建**       | 填跟踪标签 / 主题 / 描述 / 优先级 / 指派 / 目标版本 / 起止日期 / 预估工时 / 附件 / 父任务             |
| **查看**       | 详情页（字段 + 变更历史 + 注释 + 关联）、列表页、过滤器、排序、自定义列                               |
| **编辑**       | 改任意字段、改状态、加注释（注释可以是"私有注释"，只有特定角色能看）                                    |
| **状态流转**     | 新建 → 进行中 → 已解决 → 已关闭，**哪些转移合法由工作流决定**                                  |
| **关联**       | 一条 Issue 关联另一条，类型有：相关(relates)、阻塞(blocks)、重复(duplicates)、前置(precedes)等 |
| **子任务**      | 把大 Issue 拆成若干子任务，父任务显示完成百分比                                            |
| **附件**       | 上传 / 下载 / 删除                                                           |
| **观察者**      | 把某人加成观察者，他会收到这条 Issue 的所有通知                                            |
| **批量操作**     | 勾选多条 → 批量改状态 / 批量改指派                                                   |
| **导出**       | 导出 CSV / PDF                                                           |
| **复制/移动/删除** | 复制成新 Issue、移动到别的项目、删除                                                  |
| **工时**       | 在 Issue 上登记耗时                                                          |
| **权限控制**     | 不同角色能做的操作不同（越权测试的对象）                                                   |
| **REST API** | 用 HTTP 请求做增删改查（接口测试的对象）                                                |

**你要测的用例，是照着这 14 个功能点逐项设计出来的** —— 每个功能点都有对应用例，**不是"从表里挑几条测测"**。
界面层 69 条的功能点 → 用例映射表见 `test-cases/3.2-界面用例-Issue模块-69条.md` 第一节；接口层 87 条见 `test-cases/3.3-接口用例-87条.md`。

## 第四章 术语词典（看别的文档卡住了，回这里查）

> **用法**：这一章不用背。看到不懂的词就回来查。每个词给四样东西：**中文界面叫什么 / 英文叫什么 / 大白话解释 / 在哪配**。

### 4.1 有两个词是我生造的，Redmine 里没有

前面几版文档里出现过"工作流矩阵"、"权限矩阵"这种说法 —— **你的质疑是对的**，这两个词确实不该直接甩出来。澄清如下：

| 我写过的词       | 实际情况                                                                                                                          |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **"工作流矩阵"** | Redmine 界面上**只叫「工作流」（Workflow）**，没有"矩阵"这个词。"矩阵"是我为描述那张**二维勾选表的样子**（行和列都是状态）借用的数学词，属于我的描述用语，**不是你需要记的术语**。本文档统一改叫「**工作流配置表**」。 |
| **"权限矩阵"**  | 同理，指的是「角色与权限」页面上那张"每行一个权限项、每列一个角色"的勾选表。Redmine 界面就叫「**角色与权限**」。                                                               |

**以后见到"表""配置表"，指的就是这种二维勾选表格。**

### 4.2 核心对象类

| 中文界面          | 英文                    | 大白话解释                                                     | 在哪配 / 在哪看        |
| ------------- | --------------------- | --------------------------------------------------------- | ---------------- |
| **项目**        | Project               | 最外层的容器。Issue、Wiki、成员、版本全都挂在某个项目下。一个 Redmine 里可以有多个项目，互相隔离 | 管理 → 项目；或首页项目列表  |
| **问题 / 工单**   | Issue                 | **系统的核心对象**。一条"要处理的事"，可能是 bug、新需求或支持请求                    | 项目 → 问题          |
| **跟踪标签**      | Tracker               | Issue 的**类型**。默认三类：Bug（缺陷）/ Feature（功能需求）/ Support（支持请求）  | 管理 → 跟踪标签        |
| **问题状态**      | Issue status          | Issue 处在哪个阶段。默认六个：新建 / 进行中 / 已解决 / 反馈 / 已关闭 / 已拒绝         | 管理 → 问题状态        |
| **优先级**       | Priority              | 紧急程度：低 / 正常 / 高 / 紧急 / 立即                                 | 管理 → 枚举值 → 问题优先级 |
| **目标版本**      | Target version        | 这条 Issue 计划在哪个版本发布前完成                                     | 项目 → 设置 → 版本     |
| **问题类别**      | Category              | 给 Issue 分类，如"前端/后端/数据库"。用于过滤和统计                           | 项目 → 设置 → 问题类别   |
| **父任务 / 子任务** | Parent task / Subtask | 大 Issue 拆成小 Issue，父子关系                                    | Issue 表单里的一个字段   |

### 4.3 权限与流程类（本章重点）

| 中文界面 | 英文 | 大白话解释 | 在哪配 |
|---|---|---|---|
| **角色** | Role | **一类人的称呼**，本质是"一篮子权限的集合"。例如"报告者"这个角色，装了 20 项权限 | 管理 → 角色与权限 |
| **权限** | Permission | 一件具体能做的事。例如「新建问题」「删除问题」「管理成员」 | 管理 → 角色与权限里勾选 |
| **成员** | Member | 把**某个用户**和**某个角色**绑定，并加进**某个项目**。例：把 `reporter1` 以「报告者」角色加进「电商后台」项目 | 项目 → 设置 → 成员 |
| **工作流** | Workflow | **定义"哪种角色，能把 Issue 从哪个状态改到哪个状态"的规则表** | 管理 → 工作流 |
| **状态转移** | Transition | 一次状态变化，例如 新建 → 进行中 就是一条转移 | 工作流页面上勾选 |
| **状态机** | State machine | 一个通用概念（不限 Redmine）：**有限个状态 + 它们之间允许的转移路径**。工作流就是状态机的一种实现 | — |
| **枚举值** | Enumeration | 系统里可自定义的**下拉选项**集合，包括：问题优先级、活动类型（工时分类）、文档分类 | 管理 → 枚举值 |

**这里有一个最重要的区分，必须讲清楚 —— 权限和工作流是两层不同的门：**

| | **角色权限** | **工作流** |
|---|---|---|
| **管什么** | 你**能不能进这道门**：能不能看 Issue、能不能改 Issue、能不能删 | 进门之后，你**能走哪条路**：能从哪个状态改到哪个状态 |
| **在哪配** | 管理 → 角色与权限 | 管理 → 工作流 |
| **举例** | 「报告者」勾了「新建问题」→ 他能提 Issue | 就算他能改 Issue，工作流也可能规定他只能改成「反馈」，不能改成「已关闭」 |
| **不配的后果** | 没勾「新建问题」→ 连 bug 都提不了 | 权限够了，但**状态下拉框里一个选项都没有**，改不了 |

> **两者是「与」的关系**：必须**有权限 且 工作流允许**，操作才能成功。
>
> 所以：**越权测试打的是第一层门**（P 组用例），**状态机测试打的是第二层门**（S 组用例）。

#### 实测：三个角色在同一条 Issue 上能做什么

这是**在你本地环境实测出来的**结果（不是理论值）—— 拿同一条「新建」状态的 Issue，用三个账号分别登录打开，看状态下拉框里有什么：

| 账号 | 角色 | 状态下拉框里的选项 | 能力摘要 |
|---|---|---|---|
| `reporter1` | 报告者 | **反馈** | 能提单、能补充说明、能退回要求补充；**不能认领、不能关闭、不能改别人的** |
| `developer1` | 开发者 | **进行中、已拒绝** | 能认领开工、标记已解决、判定无效、打回；**不能关闭** |
| `manager1` | 管理者 | **进行中、已解决、反馈、已关闭、已拒绝** | 全部可用，含**跳步关闭** |

> **一眼看懂"权限梯度"**：同一个下拉框，三个角色看到的选项数是 **1 个 / 2 个 / 5 个**。
>
> 这就是为什么"角色"这个概念有必要 —— 不是简单的"能操作 / 不能操作"，而是**同一个人能做哪几件事，是逐条配置出来的**。

### 4.4 界面上的小东西

| 中文界面 | 英文 | 解释 |
|---|---|---|
| **注释 / 说明** | Note | 在 Issue 里追加的一段文字说明，会进"变更历史"，带作者和时间 |
| **私有注释** | Private note | 只有拥有"查看私有注解"权限的角色能看到的注释（默认只有 Manager 能看） |
| **观察者** | Watcher | 被"订阅"了这条 Issue 的人，所有变动都会通知他 |
| **查询** | Query / Custom query | 你在问题列表上设了一堆过滤条件后，可以**存成一个命名的查询**，下次直接点 |
| **变更历史** | History | Issue 详情页下方，记录每次谁改了什么字段，从旧值到新值 |
| **REST API** | REST API | 用 HTTP 请求操作数据（GET 查、POST 建、PUT 改、DELETE 删），不用点界面 |
| **API Key** | API access key | 接口认证用的密钥，在「我的账户」页面右侧能看到/重置 |

### 4.5 我脚本里用过、你可能没见过的词

| 词 | 意思 |
|---|---|
| **幂等（idempotent）** | 一个操作**重复执行多次，结果和执行一次一样**。我在配置脚本里说"幂等"，意思是"你重复跑这个脚本不会产生重复数据，放心跑" |
| **seed（种子数据）** | 预先准备好的一批基础数据，比如"把 Bug/Feature/Support 三个跟踪标签插进去"。脚本文件名 `seed-default-data.rb` 就是这个意思 |
| **rails runner** | Redmine 的一句命令行工具，可以**在不打开网页的情况下执行 Ruby 代码**，用来批量改数据库 |
| **`builtin=1` 的角色** | Redmine 内置不可删的角色（非成员、匿名）。`builtin=0` 的是可以改删的（报告者、开发者、管理者） |

### 4.6 测试领域的常用词（这些和 Redmine 无关，是测试方法）

| 词 | 意思 |
|---|---|
| **等价类划分** | 把输入值分成若干"类"，类内任取一个值效果相同。这样不用穷举所有值，每类测一个代表即可。例：主题"非空"是一类，"空/纯空格"是另一类 |
| **边界值分析** | 在取值范围的两个端点取测试值，因为**边界最容易出 bug**。例：主题上限 255 字符 → 测 255（应通过）和 256（应拒绝） |
| **场景法** | 把多个功能按真实用户的操作路径串起来测，如"提 bug → 修复 → 验证 → 关闭"整条链 |
| **错误推测法** | 凭经验猜"这里容易出错"。例：起始日期晚于截止日期、工时填负数、手改 URL 绕过权限 |
| **状态机测试** | 穷举状态的**合法转移**（应成功）和**非法转移**（应被拦），是 Redmine 这类系统的测试重点 |
| **越权测试** | 验证"不该有权限的人做不该做的事"会被拦住。既测界面上按钮藏没藏，更测**手改 URL 直接访问**会不会绕过 |
| **前置条件** | 执行一条用例之前，环境必须满足的状态。例：S-05 的前置条件是"有一条新建状态的 Issue，且用 developer1 登录" |
| **预期结果 / 实际结果** | 你**认为**应该发生什么 / **实际**发生了什么。两者不一致就是疑似缺陷 |

## 第六章 我们为什么只测 Issue 模块

### 6.1 范围收敛的原因

Remine 有 12 个项目级模块 + 10 个管理后台功能，全测是不现实的 —— **一个人、几天时间，能把一个模块测透，比"每个模块都点两下"有价值得多。**

测 Redmine 的 10 个模块、每模块几条，覆盖面看起来广，但每个模块都只能点到为止；**只测 Issue 模块**、设计 156 条用例、覆盖功能 / 状态流转 / 权限 / 接口四个维度，才是深度覆盖。

### 6.2 为什么选 Issue 模块

| 理由 | 说明 |
|---|---|
| **它是系统的存在理由** | Redmine 本质就是缺陷跟踪系统，其他模块都是围着 Issue 转的 |
| **业务流完整** | 有明确的状态流转，**状态机测试**有天然抓手（这是最能体现测试水平的类型） |
| **权限分层清晰** | 三种角色对同一条 Issue 的权限完全不同，**越权测试**素材充足 |
| **自带 REST API** | 不用自己搭后端就能做**接口测试** |
| **性能压测有意义** | 问题列表查询是典型的高频操作，**JMeter 压测能真实落地** |

### 6.3 覆盖面（156 条用例的四个维度）

| 维度 | 覆盖什么 | 用例组 | 条数 |
|---|---|---|:--:|
| **正常** | 完整字段创建、查看、编辑、关联、子任务、过滤、导出、批量、自定义列 | F1 部分 + F2 正向 + F3 全部 | 含在 F 组内 |
| **异常** | 字段校验（空/纯空格/超长/负数/附件超限/日期倒挂）+ 非法状态转移（跳步/回退） | F1-06 ~ F1-10、F7-02、S-05 ~ S-07 | 含在 F/S 组内 |
| **越权** | 三角色权限边界、私有 Issue / 私有注释可见性、手改 URL 绕过 | P-01~09 | 9 |
| **接口** | REST API 认证 + Issue 增删改查 + 过滤 + 业务场景 + 性能 / 安全测试点 | API-01~87 | **87** |

**合计 156 条** = **界面层 69 条**（功能 50 + 状态机 10 + 越权 9，见 `test-cases/3.2-界面用例-Issue模块-69条.md`）+ **接口层 87 条**（见 `test-cases/3.3-接口用例-87条.md`）。
