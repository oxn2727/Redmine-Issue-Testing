## 一、被测系统概述

| 项目        | 内容                                              |
| --------- | ----------------------------------------------- |
| **被测系统**  | Redmine（开源项目管理 / 问题跟踪 Web 系统）                   |
| **版本**    | Redmine 6.x（Docker 官方镜像 `redmine:6`）+ MySQL 8.0 |
| **技术栈**   | Ruby on Rails + MySQL，前端为服务端渲染页面                |
| **部署方式**  | Docker Compose 本地部署，访问 `http://localhost:3000`  |
| **被测模块**  | **问题跟踪（Issue）模块**                               |
| **不测的内容** | 见第四节                                            |

> 系统的完整介绍（它是干什么的、有哪些模块、核心业务怎么跑）见 `docs/1.1-被测系统简介.md`。这里只做结论性复述：
>
> Redmine 的本质是**问题台账** —— 让团队把"发现了什么问题、谁在处理、进展到哪一步"记录下来。核心对象是 **Issue**，围绕它有三层配置：**跟踪标签**（什么类型）、**问题状态**（到哪一步了）、**工作流**（谁能把状态从哪改到哪）。

## 二、为什么只测一个模块（范围收敛说明）

Redmine 有 12 个项目级模块 + 10 项管理后台功能。**本计划只覆盖 Issue 模块，不做全模块普查。**

**理由**：

| 理由                 | 说明                                                                                          |
| ------------------ | ------------------------------------------------------------------------------------------- |
| **深度 > 广度**        | 一个人、几天时间，把一个模块测透，比每个模块点两下有价值得多。"测了 10 个模块"听起来广而浅，"只测 Issue 模块但设计了 156 条用例"听起来窄而深 |
| **Issue 是系统的存在理由** | 其他模块都是围着它转的（版本是 Issue 的字段、甘特图和日历是 Issue 的呈现方式）                                              |
| **四种测试类型都能落地**     | 功能、状态机、权限、接口 —— 一个模块能把四种方法全用到                                                               |
| **业务流完整**          | 提 → 分派 → 修复 → 验证 → 关闭，整条链可跑通，场景法有用武之地                                                       |

> **范围收敛的一句话说明**：Redmine 模块很多，本项目做了范围收敛 —— 只测 Issue 模块，因为它是系统核心，且能同时覆盖功能、状态流转、权限、接口四个维度。这样能做**深度覆盖**而不是广度普查。

## 三、测试目标

1. **功能正确性**：Issue 的创建 / 查看 / 编辑 / 删除 / 关联 / 附件 / 过滤 / 批量 / 导出，各功能符合预期
2. **状态流转正确性**：合法转移能走通，非法转移（跳步、回退）被拦住
3. **权限边界正确性**：不该有权限的角色做不该做的事会被拒绝，**包括手改 URL 绕过前端**的情况
4. **接口正确性**：REST API 的认证与 Issue 增删改查符合接口约定

## 五、测试策略（四条线怎么打）

| 测试线       | 执行方式                       | 设计方法               | 产出                   |
| --------- | -------------------------- | ------------------ | -------------------- |
| **功能测试**  | 手工在界面操作                    | 等价类划分、边界值、错误推测     | F 组 41 条用例           |
| **状态机测试** | 手工 + 数据库/接口交叉验证            | 状态机分析（穷举合法 + 非法转移） | S 组 10 条用例           |
| **越权测试**  | 手工换账号 + 手改 URL             | 场景法、错误推测           | P 组 9 条用例            |
| **接口测试**  | **pytest 自动化脚本**（89 个测试全绿） | 等价类、边界值、参数异常、场景法   | API 组 87 条用例 + 可复现工程 |

### 5.1 四种核心设计方法

| 方法        | 核心思想                                     | 在 Issue 模块用在哪                    |
| --------- | ---------------------------------------- | -------------------------------- |
| **等价类划分** | 把输入分成"有效等价类"和"无效等价类"，每类取一个代表值测，**减少用例量** | 主题：非空(有效) / 空串·纯空格(无效)；跟踪标签三选一   |
| **边界值分析** | 在**取值范围的两个端点**取值 —— 边界最容易出 bug           | 主题上限 255 字符：测 255（应通过）和 256（应拒绝） |
| **状态机分析** | 画状态图，穷举**合法转移 + 非法转移**                   | Issue 的 新建→进行中→已解决→已关闭，跳步与回退     |
| **场景法**   | 模拟真实用户路径，把多步串成一条业务流                      | 报告者提 Bug → 开发者修复 → 管理者关闭 整条链     |
| **错误推测法** | 凭经验猜"这里容易错"                              | 起始日期晚于截止日期、负工时、手改 URL 越权         |

> **提示**：每条用例都标注了用了哪种方法（见 `test-cases/3.2-界面用例-Issue模块-69条.md`）。被问"你怎么设计的"，按标注答即可。

### 5.2 重点攻坚点（最能体现水平的三条）

| 用例                     | 为什么重要                                   |
| ---------------------- | --------------------------------------- |
| **S-05 跳步非法转移**        | 需要**先收紧默认工作流**才能测出来 —— 证明你懂业务规则到测试约束的转化 |
| **P-06 手改 URL 越权**     | 测的是**服务端二次校验**，不是前端按钮藏没藏 —— 安全测试入门      |
| **F1-04 / F1-07 边界值对** | 255 通过 vs 256 拒绝，经典的边界值打法               |

## 六、测试环境

### 6.1 环境架构

```
本机 Windows
  └─ Docker Desktop
       ├─ 容器 redmin_test-db-1        MySQL 8.0      端口 3306（仅容器内）
       └─ 容器 redmin_test-redmine-1   Redmine 6.x    端口 3000 → 映射到本机
                                                       ↓
                                          浏览器访问 http://localhost:3000
```

### 6.2 环境配置的五个步骤

**详细操作见 `docs/2.2-环境搭建指南.md`**，这里只列顺序（顺序错了要返工）：

```
① 加载默认数据      跟踪标签 / 问题状态 / 优先级   （Docker 镜像不自带，必须手动补）
      ↓
② 检查角色与权限    报告者 / 开发者 / 管理者 各自的权限
      ↓
③ 配置工作流        谁能把状态从哪改到哪 —— 这是状态机测试的前提
      ↓
④ 建项目 + 加成员   把测试账号以对应角色加进项目
      ↓
⑤ 开始跑用例
```

> **重点提醒**：第 ① 步是**最容易漏**的。Redmine 的 Docker 镜像只建表结构、**不加载默认数据**，导致"工作流页面点编辑没反应"、"新建 Issue 时跟踪下拉框是空的"。这是本项目真实踩过的坑，修复过程记在 `docs/2.2-环境搭建指南.md` 第一章。

### 6.3 测试账号

| 账号 | 角色 | 用途 |
|---|---|---|
| `admin` | 系统管理员 | 配置环境、管理用户 |
| `reporter1` | 报告者 | 模拟提 Bug 的人 |
| `developer1` | 开发者 | 模拟修 Bug 的人 |
| `manager1` | 管理者 | 模拟审核关闭的人 |

**测试数据准备**：一个测试项目（identifier = `v1-0`）+ 若干条覆盖不同状态的 Issue。

## 九、风险与对策

| 风险               | 影响                    | 对策                                                                      |
| ---------------- | --------------------- | ----------------------------------------------------------------------- |
| **Docker 环境起不来** | 整个项目卡住                | 已有 `scripts/start-redmine.cmd` 一键启动 + 自检；镜像加速已配好 |
| **默认数据没加载**      | 工作流配不了、用例全跑不动         | 已有 `seed-default-data.rb`，一条命令补齐（见 `2.2` 第 1.3 节）                        |
| **工作流配置错误**      | 状态机用例结果失真（S-05 测不出非法） | 配完后用 `2.2` 第 5.4 节的三种方式验证；脚本幂等可重跑                                       |
| **改了环境忘了改文档**    | 文档与实际不符               | 配置改动同步更新 `2.2`                                                       |
| **用例执行记录靠回忆填**   | 数据不可信，事后一问就露          | **边跑边记**，跑完一条立刻填"实际结果"栏                                                 |
| **工作量大做不完**      | 交付物拿不出来                 | 优先级：F1 + S 组 > P 组 > F2/F3 > API 组。**宁可少跑，不要编数字**                       |

## 十、一条原则（写在最后）

> **用例条数是事实，通过率和缺陷数是结果。**
>
> 156 条（界面层 69 + 接口层 87）是清单里真实列出的**设计**数字。但"通过率 98%""发现 3 个 bug"这类**执行**数字，**必须跑完如实记录** —— 没跑就编，被追问一句"说说这 3 个 bug 的复现步骤"就穿帮了。
