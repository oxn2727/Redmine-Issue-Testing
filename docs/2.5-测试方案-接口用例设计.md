## 一、先看懂这套设计方法

> **如果你已经熟悉"接口测试测什么、用例怎么设计"**，1.1~1.3 可以扫过去。
> 但 **1.4 / 1.5 的判定规则要留着** —— 它把方法论落到 Redmine 的具体字段上了，这是只有做过才知道的东西。

### 1.1 接口测试在整个测试体系里的位置

**接口测试**＝**功能测试的一种实现方式**。功能测试从"入口"分两种：

| 方式       | 打哪里            | 特点                     |
| -------- | -------------- | ---------------------- |
| **界面测试** | 用户在浏览器上点       | 慢、受前端影响大、能顺便看界面        |
| **接口测试** | 直接发 HTTP 请求打后端 | 快、稳定、**能绕过前端做越权**、易自动化 |

> **为什么必须有接口测试**：前端页面会拦掉很多非法操作（按钮置灰、选项不出现）。**光测界面，你不知道是"后端真的防住了"还是"前端藏起来了"**。接口测试直接打后端，才能验证真实的防护。

### 1.2 接口测试的三个维度（也叫"测试点"）

这是行业通用的分法：

| 维度       | 测什么         | 具体测试项                                                                 | 本项目怎么做           |
| -------- | ----------- | --------------------------------------------------------------------- | ---------------- |
| **功能测试** | 接口能不能正确干活   | ① **单接口功能**：一个业务对应一个接口（登录业务→登录接口）<br>② **业务场景功能**：按用户真实场景**连续调用多个接口** | `3.3` 第一章（单接口）、第二章（场景） |
| **性能测试** | 接口快不快、扛不扛得住 | ① **响应时长** ② **吞吐量（TPS）** ③ **错误率** ④ **服务器资源占用率**                    | `3.3` 第三章              |
| **安全测试** | 会不会被绕过/被攻破  | ① **攻击安全**（木马/病毒/黑客）→ 专业安全工程师负责<br>② **业务安全**：敏感数据是否加密、SQL 注入、越权……    | `3.3` 第四章              |

> **对我们（功能测试岗）的现实分工**：性能测试**会设计测试点、会用工具跑**就够了；攻击安全**不归我们管**（那是安全工程师的活），但 **业务安全必须测** —— 越权、敏感数据泄露、SQL 注入这三样是功能测试的职责范围。

### 1.3 用例设计的两层结构（顺序不能反）

```
第一层：单接口测试          ← 先把每个接口单独打透
   ├─ 正向测试（3 类）
   └─ 反向测试（3 类）
              ↓ 必须做完才进下一步
第二层：业务场景测试        ← 再把接口串成真实业务流程
   └─ 一般只做正向（异常场景在单接口层已经覆盖过了）
```

> **为什么必须"单接口 → 业务场景"**：场景测试里一步失败，你**不知道是哪个接口的问题**。只有单接口都被独立验证过，场景失败才能定位到具体环节。跳过单接口直接测场景，等于把 10 个接口的风险搅成一锅粥。

### 1.4 单接口的六类用例（这套方法的核心）

**正向测试** —— 参数都给对，看能不能正常干活：

| 类别       | 给什么参数           |  优先级   | 为什么要测              |
| -------- | --------------- | :----: | ------------------ |
| **必选参数** | 只给**所有必填**参数    | **P0** | 最小可用集。这条不过，接口就是坏的  |
| **组合参数** | 所有必填 + **部分**可选 |   P2   | 可选参数**混着传**会不会互相干扰 |
| **全部参数** | 所有必填 + **所有**可选 |   P1   | 字段全填时会不会溢出/冲突      |

> **P0 和 P1 的区别（容易搞反）**：**必选参数 P0 最高**，因为它是接口能不能用的底线；**全部参数 P1** 次之，因为它最容易暴露字段间冲突；组合参数 P2 最低，它只是抽样验证。

**反向测试** —— 故意给错，看接口能不能挡住：

| 类别       | 给什么参数                    |  优先级   | 用什么方法设计             |
| -------- | ------------------------ | :----: | ------------------- |
| **功能异常** | 数据类型**对**，但业务上**不成立**    | **P1** | 场景法（例：手机号格式对，但已被注册） |
| **数据异常** | 数据类型**不对**（空/特殊字符/字母/长度） |   P2   | **等价类 + 边界值**       |
| **参数异常** | 参数的**结构**不对，分四小类         |   P3   | 见下表                 |

**"参数异常"的四小类**（别看名字简单，容易漏）：

| 小类 | 做法 | Redmine 上的例子 |
|---|---|---|
| **多参** | 多给参数 | 传了接口不认识的字段 |
| **少参** | 缺某个必填参数 | 只给 `subject`，不给 `project_id` |
| **无参** | 一个参数都不给 | 空 body `{}` |
| **错误参数** | 参数**名**写错 | `subjct`（少个 e）、`projectId`（驼峰） |

> **区分"功能异常"和"数据异常"的一句话**：看**格式对不对**。
> `subject` 传空串 → **格式就不合格** → 数据异常；
> `project_id` 传一个格式合法但不存在的项目 → **格式对，业务不成立** → 功能异常。

**哪些字段要测「数据异常」？—— 看规则，不看必不必选**

这张表要背下来，它回答"非必选字段要不要测数据类型不对"：

| | 值为空 | 类型 / 格式 / 长度 / 范围不对 |
|---|---|---|
| **必选字段** | ❌ **反向**（必填校验） | ✅ **反向** |
| **非必选字段** | ✅ **合法** → 就是正向「组合参数」用例 | ✅ **反向** |

- **非必选字段的"空"不是反向**：不填就是正常情况，由正向「组合参数」用例覆盖，**不要再单列一条**。
- **非必选字段填了非法值才是反向**：只要它有类型 / 格式 / 长度 / 范围约束，就得测。`3.3` 第 1.4 节里的 `priority_id=999`、`done_ratio=101`、`estimated_hours=-1`、`start_date` 格式错 —— **这四条的字段全部是非必选**，这就是"看规则不看必选"的落地。
- **没有规则的字段，一条反向都不测**：`description`（描述）无长度限制、无字符集限制 → 类型 / 长度 / 特殊字符**全不测**（`3.3` 第 1.4 节里没有它，是**故意的**，不是漏了）。被问"描述为什么没有反向用例"就答这一句。
- **"特殊字符 / 字母"先问该字段有没有字符集规则**：数字型字段（id / 完成度 / 工时）给字母 = 反向；文本型且业务规定了字符集（如"用户名"）= 反向；文本型**无**字符集限制（如 `subject` 能存中文和 `#`）= **合法，不测**。

### 1.5 优先级 P0~P3 怎么用

| 级别 | 含义 | 执行时机 |
|:---:|---|---|
| **P0** | 主干用例，挂了等于接口不可用 | **必跑**，冒烟测试级别 |
| **P1** | 重要用例，影响面大 | 必跑 |
| **P2** | 一般用例，覆盖边界与抽样 | 时间够就跑 |
| **P3** | 低优先级，锦上添花 | 有时间再跑 |

## 二、被测接口清单与字段字典

设计用例前必须先知道**接口长什么样、字段有哪些、约束是什么** —— 这就是"被测对象分析"在接口层的落地。

### 2.1 认证方式

Redmine 用 **HTTP 请求头**传 API Key（不用登录态、不用 Cookie）：

```
X-Redmine-API-Key: 37da63d886132084a9174cfc82d8aa71b9b64c4b
```

> **术语**：**API Key** 是一串代表"你是谁"的密码，放在请求头里发给服务器。比账号密码简单，因为它只能调接口、不能改密码。

**前置开关**：必须在 管理→设置→API 里勾选「启用 REST Web Service」，否则**所有**接口返回 403、且响应体是空的 —— 这个坑我实测踩到了（见 `automation/4.2-接口测试执行步骤.md` 1.1）。

### 2.2 接口清单

| 编号 | 方法 | 路径 | 作用 | 认证 |
|:---:|---|---|---|:---:|
| — | GET | `/users/current.json` | 取当前用户（**用来验证 Key 是否有效**） | 需 Key |
| — | GET | `/issues.json` | Issue 列表（支持过滤、分页） | 需 Key |
| — | POST | `/issues.json` | **创建** Issue | 需 Key |
| — | GET | `/issues/:id.json` | **查询** Issue 详情 | 需 Key |
| — | PUT | `/issues/:id.json` | **更新** Issue | 需 Key |
| — | DELETE | `/issues/:id.json` | **删除** Issue | 需 Key |
| — | GET | `/users.json` | 用户列表（**仅管理员**） | 需管理员 |

> **`:id`** 是路径参数，替换成真实数字，如 `/issues/3.json`。
> **REST**（术语）：一种 API 设计风格，用「HTTP 方法 + 资源路径」表达操作 —— GET 查、POST 增、PUT 改、DELETE 删。

### 2.3 Issue 字段字典（**设计用例的输入，重点**）

**创建 Issue 时可传的字段**：

| 字段 | 必填 | 类型 | 约束（实测） | 合法取值 |
|---|:---:|---|---|---|
| `project_id` | **✅** | int | 必须是**存在且未归档**的项目 | 1 |
| `subject` | **✅** | string | **1~255 字符**，不能为空/纯空白 | 任意中英文 |
| `tracker_id` | ☐ | int | 必须是存在的跟踪标签 | 1=Bug 2=Feature 3=Support |
| `status_id` | ☐ | int | 必须是存在的状态 | 1=New 2=In Progress 3=Resolved 4=Feedback 5=Closed 6=Rejected |
| `priority_id` | ☐ | int | 必须是存在的优先级 | 1=Low 2=Normal 3=High 4=Urgent 5=Immediate |
| `description` | ☐ | string | **无长度限制、无字符集限制**（→ **没有反向用例**） | 任意 |
| `assigned_to_id` | ☐ | int | 必须是**项目成员**的用户 | 1 |
| `category_id` | ☐ | int | 必须是该项目下的类别 | 1=前端 2=后端 3=数据库 |
| `fixed_version_id` | ☐ | int | 必须是该项目下的版本 | 1=V1.1 2=V2.0 |
| `parent_issue_id` | ☐ | int | 必须是存在的 Issue（做子任务） | 任意 issue id |
| `start_date` | ☐ | date | `YYYY-MM-DD` 格式 | `2026-09-24` |
| `due_date` | ☐ | date | `YYYY-MM-DD`，**不得早于 start_date** | `2026-10-08` |
| `estimated_hours` | ☐ | float | **≥ 0** | `8.5` |
| `done_ratio` | ☐ | int | **只能是 0~100**（按 10 递增） | `0` `30` `100` |
| `is_private` | ☐ | bool | `true` / `false` | `false` |
| `watcher_user_ids` | ☐ | array | 观察者用户 id 数组 | `[5,6]` |
| `custom_fields` | ☐ | array | 自定义字段（本环境未配置） | — |

> **⚠️ 这张表里的"约束"列是有价值的**：`subject` 的 255、`done_ratio` 的 0~100、`due_date ≥ start_date` 这三条**都是实测出来的**，官方文档不会一一告诉你。**设计边界值用例就靠它。**
> **注意**：本表是**接口口径**，字段以官方 REST 文档 + 实测为准，**与界面表单的字段清单不是一套**（界面 13 个字段见 `docs/1.2-需求规格说明书-Issue模块.md` 附录 A）。两边互不引用。

**查询 Issue 详情时返回的字段**（用于设计断言）：

```
id / project{id,name} / tracker{id,name} / status{id,name,is_closed} / priority{id,name}
author{id,name} / assigned_to{id,name} / subject / description / start_date / due_date
done_ratio / is_private / estimated_hours / total_estimated_hours / spent_hours
total_spent_hours / created_on / updated_on / closed_on
```

### 2.4 状态码速查（接口测试的"读题卡"）

| 码 | 含义 | 本接口什么时候出现（**实测**） |
|:---:|---|---|
| **200** | 成功 | GET 查询/列表、PUT 部分场景、删除后的 GET |
| **201** | 创建成功 | POST `/issues.json` 成功 |
| **204** | 成功但**不返回内容** | **PUT 更新成功、DELETE 删除成功（⚠️ 不是 200！）** |
| **400** | 请求本身不合法 | body 不是合法 JSON（服务器读不懂） |
| **401** | 未认证 | Key 错误 / 缺失 Key 头 / 访问受保护接口 |
| **403** | 无权限 | 角色权限不足（删他人 Issue）／**API 未启用（所有请求都 403）** |
| **404** | 资源不存在 | 查/改/删不存在的 Issue；**过滤不存在的 project_id** |
| **422** | 参数不合法 | 缺必填、字段值非法、业务规则不满足 |

> **🔴 全文档最重要的一条警告**：**Redmine 更新/删除成功返回 204，不是 200。**
> 而且更坑的是 —— **返回 204 不代表真的改了**。无权限、非法状态转移，Redmine 也返回 204，但数据**原封不动**。
> → **凡 PUT/DELETE 类用例，必须"回读验证"**（改完再 GET 一次看值变没变）。只看状态码会把 10 条越权用例全部误判为"通过"。

## 三、方法小结（三条）

1. **接口用例怎么设计的**：行业通用的两层设计法 —— 先做**单接口测试**，每个接口覆盖正向三类（必选 / 组合 / 全部参数）与反向三类（功能异常 / 数据异常 / 参数异常）；单接口打透之后再做**业务场景测试**，把接口串成真实业务流程，一般只设计正向场景。

2. **覆盖了多少**：Issue 模块接口部分设计了 **77 条功能用例 + 4 个性能测试点 + 6 个安全测试点**；功能用例里，单接口 69 条、业务场景 8 条。

3. **发现了什么问题**：实测发现两处接口层面的不一致 ——
   - **无效枚举值处理不一致**：`priority_id` 传不存在的值会报 422，但 `status_id` / `tracker_id` 传不存在的值会返回成功并**静默替换成默认值**，调用方无法感知参数被丢弃；
   - **无权操作的拒绝方式不统一**：无权限修改他人 Issue 时返回 204（看起来成功）但数据未变，无权限删除时返回 403 明确报错。

   → **这也说明接口测试不能只看状态码，必须回读验证。**

## 四、实测发现的接口行为不一致点

这一节把本次实测里**反直觉、值得单独记录**的行为集中列出。它们**不全是缺陷** —— 有的是设计如此，有的是真的不一致。**能分清这两者，才是测试的价值**。

|  #  | 现象                        | 实测数据                                                                                       | 性质               | 怎么解释                                 |
| :-: | ------------------------- | ------------------------------------------------------------------------------------------ | ---------------- | ------------------------------------- |
|  1  | **无效枚举值处理不一致**            | `priority_id=999`→**422**；`status_id=999`→**201（回落 New）**；`tracker_id=999`→**201（回落 Bug）** | ⚠️ **真的不一致**     | "同一接口对三个相似字段用了三种处理方式，调用方无法预知参数会不会被丢弃" |
|  2  | **无权操作的拒绝方式不统一**          | 无权**改**→**204**（静默不改）；无权**删**→**403**（明确报错）                                                | ⚠️ **真的不一致**     | "同一系统两种拒绝风格，客户端无法统一处理"                |
|  3  | **204 不代表成功**             | 非法状态转移、越权修改，都返回 **204**，但数据**一点没变**                                                        | ⚠️ **需特殊断言**     | "接口测试必须回读验证，只看状态码会把 10 条越权用例全部误判为通过"  |
|  4  | **更新/删除成功返回 204 而非 200**  | PUT/DELETE 成功 → **204 No Content**                                                         | ✅ 设计如此（REST 规范）  | 不用当缺陷报，但断言时别写错                        |
|  5  | **参数无效的处理不统一**            | `limit=0`/`offset=-1`→**200**（容错）；`project_id=999`→**404**（报错）                             | ⚠️ 边界模糊          | "分页参数容错、过滤条件报错，同接口两套策略"               |
|  6  | **非法 JSON 返回 400 而非 422** | `{bad json` → **400**                                                                      | ✅ 设计如此           | 400 = 请求读不懂；422 = 字段值不合法。别混           |
|  7  | **匿名可访问范围**               | `/issues.json`、`/projects.json` 匿名→**200**；`/users.json`、`/time_entries.json` 匿名→**401**   | ✅ **设计如此（不是漏洞）** | "公开数据匿名可读是设计意图；**别把'设计如此'当漏洞报**"      |
|  8  | **创建不产生变更记录**             | 新建 Issue 后 `include=journals` 为**空**；改 3 次 = 3 条                                           | ✅ 设计如此           | 断言历史条数时要按"变更次数"算，不是"变更+1"             |
