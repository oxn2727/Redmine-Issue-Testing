## 〇、用例设计方法

> **这一节是方法，用例的条数全部由它推出来。** 方法不认，数字就是拍脑袋。

### 0.1 正向 / 逆向的划分依据

**划分依据只有一个：喂进系统的数据合不合法**（不是"这条在测哪个字段/哪个功能"）。

| | 正向 | 逆向 |
|---|---|---|
| 输入 | **合法值**（有效等价类的代表） | **非法值**（无效等价类 / 边界外的值） |
| 预期 | 功能**正常完成**（创建成功 / 保存成功） | **被拒绝** + 提示正确 + **数据不被改坏** |
| 怎么推 | 等价类的**有效类**各取代表值；边界的**上点 / 内点** | 等价类的**无效类**各取代表值；边界的**离点**（界外那个值） |

**判据**：把这条用例里的数据挨个看一遍 —— **有"一个"非法值 → 逆向；全是合法值 → 正向**。

**三点容易搞混：**
1. 正向 / 逆向的推导工具就是**等价类 + 边界值**。主题 255 是上点（正向），256 是离点（逆向）。
2. 同一个字段**同时**有正向和逆向测试点（主题：正向 1/128/255，逆向 空/纯空格/256）。
3. 正/逆是**一个取值**的属性，不是"一整组"的属性。

**反向在界面层只落三类**（第四类"参数异常"构造不出，归接口层）：

| 类别 | 界面层例子 | 划分依据 |
|---|---|---|
| **数据异常** | 主题为空 / 纯空格 / 256 字符；工时负数 | 等价类、边界值 |
| **功能异常** | 截止日期早于开始日期；指派给非成员；跳工作流改状态 | 按「业务规则不成立」划分 |
| **权限** | Reporter 删单 / 改他人单 | P 组，条件组合 + 用户权限 |

> **查询类功能（过滤器 / 搜索）没有经典的逆向** —— 它没有"非法输入被拒绝"这回事。它的"逆向"是**空结果与空态**（无匹配关键词、空关键字、不选任何条件）。这是两种性质，别硬套登录那种"空值被拒"。

### 0.2 四条设计规则

|   #   | 规则                                                                            | 依据                                                                                |
| :---: | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **1** | **正向 = 组合**。一条正向用例里**多个字段同时取有效值**；条数 = **取值最多的那个字段的取值个数**，其余字段的有效值**轮转**进这几条。 | 等价类的取法：同类有效值可合并，条数由**有效类最多的字段**决定 |
| **2** | **逆向 = 控制变量**。每条**只让一个字段取无效值**，其余全有效 —— 失败才能直接定位到字段。                          | 失败必须能直接定位到字段 → 一行只放一个无效值                                              |
| **3** | **同一条用例里的多个取值，预期结果必须相同**才可组合；预期不同的（提示语各异）一律拆开。                                | 预期不同的取值不能共用同一格「实际结果」                                             |
| **4** | **单字段练习**（只有一个输入框）才每个边界点各一条，**不做组合**。                                         | 单字段没有可组合的维度，逐点各一条                           |

**主流程再补两条**（对应接口口径的「必选参数 / 全部参数」）：**最小集**（只填必填项，顺带验默认值）+ **完整集**（全填）。

> **状态**在新建页只有一个合法初始值（New），不算独立用例，放在最小集里验默认值。

### 0.7 每条用例用哪个账号跑（**按「缺陷流转」分角色，别全用 admin，也别全用 developer**）

> **两个坑**：① **admin 是超管**，能删任何单、能直接改状态 → 用它跑，S 组 / P 组结论全部失真；② **不能全用 developer** —— 提单本是**报告者（reporter）**的活，让 developer 去提 bug 不符合业务。**先按真实流转分角色，再按权限微调。**

**这四类账号的分工 = 一条缺陷的生命周期**：`reporter1 提单 → developer1 认领修复 → manager1 验收关闭`，`admin` 只做环境预置。

| 用例组 | 执行账号 | 依据（权限） |
|---|---|---|
| **F1 创建** | **`reporter1`** | 提单是报告者的活（`add_issues`）；**「指派给」在本项目几个角色都能设**（字段是否可改由工作流字段权限决定，默认都可改），所以 F1 的完整集正常带 `Assignee` |
| **F2 查看** | **`reporter1`** | `view_issues` |
| **F3 编辑 / F5 关联 / F6 子任务 / F7 附件** | **`developer1`** | 认领修复：`edit_issues`、`manage_issue_relations`、`manage_subtasks`（**这三项 Reporter 都没有**，只能 Developer/Manager 做） |
| **F4 复制 / 移动** | **`developer1`** | 常规维护 |
| **F4-01 删除 Issue** | **`manager1`** | **`delete_issues` 官方默认只有 Manager 有**（Developer 也没有） |
| **F8 工时** | **`reporter1`** | `log_time`（三个角色都有） |
| **F9 关注者** | **`manager1`** | **`add_issue_watchers` 官方默认只有 Manager 有** —— 这正是在 developer1 上看不到「Add watcher」的原因，**不是 bug** |
| **F10~F13 列表 / 搜索 / 导出** | **`reporter1`** | `view_issues`；过滤结果随当前用户可见范围变化 |
| **F10-08 按「私有」过滤** | **预置用 `admin`，查询用 `reporter1`** | 私有 Issue 只有 admin 能建（接口预置） |
| **S 状态流转（全部）** | **逐条按「前置条件」列**：S-01/02/04/05/06/07/08/09 → `developer1`；S-03 → `manager1`；S-10 → `reporter1` | **状态机结论本来就是"某账号能看到哪些状态"**，换账号答案就变 |
| **P 权限（全部）** | **逐条按「前置条件」列**：P-01/02/03/06 → `reporter1`；P-07/P-09 → 写方 `manager1`、读方 `reporter1`；P-08 → `manager1` | **越权用例的被测对象就是"受限账号"** |
| **P-04 非成员访问** | 一个**非本项目成员**的账号 | admin 是成员，测不出 |

**记忆口诀**：**提单找 reporter，改单找 developer，删单和加关注者找 manager；测"不能"（越权/受限）就用受限账号；admin 只在预置数据时出场。**

> **官方默认角色权限速查**（据 `lib/redmine/default_data/loader.rb` 原文，逐项核对过；本项目在此基础上给 Reporter 加了 `edit_own_issues`）：

| 权限 | Reporter | Developer | Manager |
|---|:-:|:-:|:-:|
| `view_issues` 查看问题 | ✅ | ✅ | ✅ |
| `add_issues` 添加问题 | ✅ | ✅ | ✅ |
| `edit_issues` 更新问题（改任何人的） | ❌ | ✅ | ✅ |
| `edit_own_issues` 更新自己的问题 | ✅（本项目加） | —（默认清单无，但有 `edit_issues` 等效） | ✅ |
| `manage_issue_relations` 管理问题关联 | ❌ | ✅ | ✅ |
| `manage_subtasks` 管理子任务 | ❌ | ✅ | ✅ |
| `delete_issues` 删除问题 | ❌ | ❌ | ✅ |
| `add_issue_watchers` 添加关注者 | ❌ | ❌ | ✅ |
| `set_issues_private` 设为私有 | ❌ | ❌ | ✅ |
| `log_time` 记录工时 | ✅ | ✅ | ✅ |

> **⚠️ 没有「指派问题」这个权限**：**Redmine 不存在 `assign_issues`**（那是 Jira 的概念）。「指派给」字段**谁能改，由该角色的「工作流 → 字段权限」决定**（默认几个角色都可改），所以规范做法里「指派给」是**创建单的一部分**（完整集里带上），不是单独一组。**本项目实测：developer1 的 New issue 表单上有 Assignee。**
>
> **上述权限表建议再实测核对**：在「管理 → 角色与权限」里逐角色核对一遍，以实际勾选为准。

> **admin 界面是中文这件事**：admin 的 `users.language` 存的是 `zh`，属于**单账号设置**，不是全局。执行用例时**不要为了看中文而切 admin** —— 两个理由：① 接口测试有 **18 处断言直接比对英文名称**（`New`/`Bug`/`In Progress`），全局切中文会让这批断言集体失败；② 你要跑的三个账号（reporter1 / developer1 / manager1）本来就都是英文。
> **正确做法**：三个业务账号各锁 English，**只用 `admin` 做接口预置**（预置不需要看界面）。

## 一、分组逻辑：为什么按「功能点」分组

**一个功能点 = 一组；组内再分正向 / 逆向。** 拆测试点按功能点走：功能点 → 字段 / 交互项 → 逐项对照维度。

上一版把"查看 / 编辑 / 关联 / 附件 / 子任务"全塞进一个 F2，等于把 **11 个功能点**混成一组，分不清哪条在测什么。本版拆开：

```
Issue 模块
├─ F1  创建          ├─ F7  附件
├─ F2  查看          ├─ F8  工时
├─ F3  编辑          ├─ F9  关注者
├─ F4  复制/移动/删除  ├─ F10 列表视图（过滤器/排序/自定义列）
├─ F5  关联          ├─ F11 搜索
├─ F6  子任务        ├─ F12 批量操作
                    └─ F13 导出
├─ S   状态流转（跨功能点的状态机）
└─ P   权限控制（跨功能点的越权）
```

**S / P 单独成组**：它们的测试对象不是某个功能点，而是**贯穿全模块的状态机与权限**，所以不并入 F 组。

**编号变更说明**（本版相对上一版）：

| 变化 | 说明 |
|---|---|
| **净增 8 条**：61 → 69 | 过滤器组 7 → **14**（**+7**）；补 **F6 父任务字段**（**+1**）、**F9 关注者候选**（**+1**）；原 F2-04「手动改状态」与 S-01 同一操作，**合并去重**（**−1**） |
| F2 拆成 F2~F9 | 查看/编辑/复制移动删除/关联/子任务/附件/工时/关注者 |
| F3（旧列表）拆成 F10~F13 | 列表视图/搜索/批量/导出 |
| 原 F2-04 → 合并进 S-01 | 改状态就是一次状态转移，S 组本就是测这个 |
