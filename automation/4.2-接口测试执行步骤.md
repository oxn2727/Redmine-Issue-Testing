## 第一章 执行前准备（一次性，约 10 分钟）

### 1.0 先确认下面这几样东西是好的

| 检查项         | 命令（在 Git Bash 或 CMD 里跑）       | 期望                                                          |
| ----------- | ----------------------------- | ----------------------------------------------------------- |
| Docker 在跑   | `docker ps`                   | 能看到 `redmin_test-redmine-1`、`redmin_test-db-1` 两个容器，状态 `Up` |
| Redmine 活着  | 浏览器打开 `http://localhost:3000` | 出现 Redmine 首页                                               |
| 能用 admin 登录 | 右上角登录，账号 `admin`              | 能进管理界面                                                      |

**容器不在跑**？先执行 `scripts/start-redmine.cmd`（双击即可）。

### 1.1 启用 REST API —— **不做这步，所有接口都返回 403**

**这是最容易踩的坑，我实测踩到了。** Redmine 装好后 REST API 默认是**关闭**的，此时你发任何接口请求，都会收到一个 **403 并且响应体是空的** —— 你会以为 Key 错了，其实 Key 根本还没被用上。

**手工开启**：

```
1. admin 登录 → 右上角「管理」→ 左侧「设置」
2. 切到「API」标签页
3. 勾选「启用 REST Web Service」
4. 点「保存」
```

**怎么验证开了**：

```bash
curl -s -o /dev/null -w "%{http_code}\n" -H "X-Redmine-API-Key: 任意字符串" http://localhost:3000/users/current.json
```

- 返回 **403** 且 `curl -i` 看到 `content-length: 0` → **还没启用**
- 返回 **401** → 已启用（401 说明服务器在检查你的 Key，只是 Key 不对）

> **403 和 401 的区别（记牢）**：
> **401** = "你是谁？我不认识"（没认证 / Key 无效）
> **403** = "我知道你是谁，但你不能干这个"（已认证、没权限）
> 所以"API 没启用"返回 403 是 Redmine 的一个反直觉设计 —— 它把"功能关着"也归成了"权限不够"。

### 1.2 给各账号生成 API Key

**手工生成**（每个账号都要做一次）：

```
1. 用该账号登录 Redmine
2. 右上角「我的账号」
3. 右侧「API 访问键」→ 点「生成」
4. 复制那串 40 位字符串
```

**本项目需要 4 个 Key**：`admin`、`reporter1`、`developer1`、`manager1`（做越权测试必须用不同角色的 Key）。

**为什么必须做**：不是项目成员，这些账号连项目里的 Issue 都看不到，越权用例根本跑不起来。

```

3. 点「新建成员」，分别添加：
     reporter1  → 角色 Reporter

### 1.4 一键搞定 1.1~1.3（推荐）

上面三步手工做一遍是**必要的理解过程**，但以后重建环境会烦。所以做了个脚本：

```

    admin        37da63d886132084a9174cfc82d8aa71b9b64c4b

    reporter1    已在项目中，角色 = Reporter

## 第二章 执行方式一：curl（最快，适合单条验证）

**curl**（术语）：命令行发 HTTP 请求的工具，Windows 10 以上自带。

### 2.1 四条常用模板

```bash
# 把 Key 存成变量，后面省事（Git Bash 语法）
KEY=37da63d886132084a9174cfc82d8aa71b9b64c4b

# ---- GET：查 ----
curl -s -H "X-Redmine-API-Key: $KEY" http://localhost:3000/issues/3.json

# ---- POST：建 ----
curl -s -X POST -H "X-Redmine-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"issue":{"project_id":1,"subject":"curl 建的"}}' \
  http://localhost:3000/issues.json

# ---- PUT：改（注意：成功是 204，没有响应体）----
curl -s -o /dev/null -w "%{http_code}\n" -X PUT \
  -H "X-Redmine-API-Key: $KEY" -H "Content-Type: application/json" \
  -d '{"issue":{"subject":"curl 改的"}}' \
  http://localhost:3000/issues/3.json

# ---- DELETE：删 ----
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE \
  -H "X-Redmine-API-Key: $KEY" \
  http://localhost:3000/issues/3.json
```

> **`-s -o /dev/null -w "%{http_code}\n"` 是什么**：
> `-s` 静默（不打印进度条）、`-o /dev/null` 丢弃响应体（不然会打一屏）、`-w "%{http_code}"` 只打印状态码。
> **PUT/DELETE 类请求尤其需要这个** —— 因为成功返回 **204 且响应体是空的**，肉眼看什么都没输出，会以为自己发错了。

### 2.2 Windows 下跑 curl 的注意事项

| 问题 | 表现 | 解决 |
|---|---|---|
| 单引号不认 | `-d '{"issue":...}'` 报错 | Windows **CMD** 用双引号，里面的 `"` 转义成 `\"`；或者直接用 **Git Bash**（推荐） |
| 中文乱码 | subject 变问号 | 加 `-H "Content-Type: application/json; charset=utf-8"`，或改用 Postman |
| 路径被转换 | Git Bash 下 `-d @/tmp/x.json` 找不到文件 | 先 `export MSYS_NO_PATHCONV=1` |

> **我的建议**：**少量验证用 curl，批量执行用 Postman 或 pytest**。curl 的优势是"快、能贴进终端、方便截图做证据"。

## 第三章 执行方式二：Postman 手工执行

**Postman**（术语）：图形化的接口调试工具，把请求配好保存下来，下次点一下就能重发，还能写断言。

### 3.1 第一步：建环境变量（把 Key 从请求里抽出来）

```
1. 打开 Postman → 右上角「Environments」→「+」新建环境，命名 Redmine
2. 加两个变量：
     变量名        初始值
     base_url      http://localhost:3000
     api_key       你的 admin API Key
3. 点「Save」
4. 右上角环境下拉框选中 Redmine（**不选的话 {{base_url}} 不会被替换**）
```

> **为什么要环境变量**：后面要换账号测越权（admin → reporter1），如果 Key 写死在各请求里，就要改几十处。用变量只改一个地方。

### 3.2 第二步：建 Collection，统一配置请求头

```
1. 左侧「Collections」→「+」新建，命名「Redmine Issue 接口测试」
2. 右键这个 Collection →「Edit」→「Headers」标签
3. 加两条：
     X-Redmine-API-Key : {{api_key}}
     Content-Type      : application/json
4. 保存
```

> **Collection 级请求头会被里面所有请求继承** —— 这跟代码里的"接口对象层"是同一个思路：公共配置只写一次。

### 3.3 第三步：执行一条用例（以 API-06 为例）

```
1. 右键 Collection →「Add request」，命名「API-06 必选参数创建」
2. 方法选 POST，URL 填 {{base_url}}/issues.json
3. 「Body」→ 选「raw」→ 右侧格式选「JSON」，填：
       {"issue": {"project_id": 1, "subject": "接口测试-必选参数"}}
4. 点「Send」
5. 看下方响应：状态码应当是 201 Created
```

**在「Tests」标签页写断言**（不写断言的话，Postman 只显示响应，不会告诉你对错）：

```javascript
// pm.test 定义一个测试项；第一个参数是名字，第二个参数是函数
pm.test("API-06 状态码 201", function () {
    pm.response.to.have.status(201);
});

pm.test("API-06 返回了 issue.id", function () {
    const json = pm.response.json();
    pm.expect(json).to.have.property("issue");
    pm.expect(json.issue).to.have.property("id");
});
```

**运行后 Send 下方的「Test Results」标签会显示这两条是否通过（绿色 Passed / 红色 Failed）。**

### 3.4 第四步：越权用例必须做「回读验证」（★ 本项目最关键的一步）

**先看一个真实的坑**：

| 用例 | 请求 | 返回 | 看起来 | 实际 |
|---|---|---|---|---|
| API-48 developer1 改他人标题 | PUT | **204** | 成功 | 标题**真的变了** |
| API-49 reporter1 改他人标题 | PUT | **204** | 成功 | 标题**一点没变** |

**两种情况返回的东西一模一样**。所以只断言"状态码 204"的用例，**会把越权漏洞漏掉**。

**正确写法（Postman 里两步走）**：

```
第 1 个请求：PUT {{base_url}}/issues/{{issue_id}}.json
             Body: {"issue":{"subject":"reporter1 篡改的标题"}}
             （用 reporter1 的 Key —— 在请求自己的 Headers 里覆盖：
                X-Redmine-API-Key : {{api_key_reporter}}）

第 2 个请求：GET {{base_url}}/issues/{{issue_id}}.json
             Tests 里断言标题还是原值：
```

```javascript
pm.test("API-49 越权修改应当无效（标题未被改）", function () {
    const json = pm.response.json();
    pm.expect(json.issue.subject).to.eql("管理员提的单");
});
```

> **一句话记住**：**PUT/DELETE 的用例，永远要多发一个 GET 去核实**。
> 这是接口测试和"点按钮测试"最大的思维差异 —— 状态码会骗人，数据不会。

### 3.5 第五步：批量跑整个 Collection

```
1. 左侧 Collection 右侧「...」→「Run collection」
2. 勾选要跑的请求 →「Run Redmine Issue 接口测试」
3. 跑完出报告：Passed / Failed 各多少，点进去看哪条挂了
```

> 这是 Postman 版的"回归测试"：改完接口配置，一键重跑，看有没有跑挂的。
> **但 Postman 的用例不好做数据清理**（跑一次会在库里堆十几条 Issue）。所以**批量执行建议用第四章的 pytest**，Postman 主要用于演示和单条调试。

## 第四章 执行方式三：pytest 自动化（**主力方式**）

**为什么主力用它**：77 条接口用例，手工点要 1~2 小时，脚本跑 **16 秒**；而且**自动清理测试数据**，可以反复跑。

### 4.1 工程长什么样

```
automation\
├── config.py                ← 唯一要改的文件（地址 + 4 个 Key）
├── api_client.py            ← 接口封装层（RedmineAPI 类）
├── conftest.py              ← pytest 的公共 fixture（客户端、临时数据清理）
├── test_auth.py             ← API-01~05   认证 / 越权访问
├── test_issue_create.py     ← API-06~35   创建
├── test_issue_read.py       ← API-36~42   查询
├── test_issue_update.py     ← API-43~55   更新（★ 含回读验证）
├── test_issue_delete.py     ← API-56~61   删除
├── test_issue_list.py       ← API-62~69   列表过滤
├── test_scenario.py         ← API-70~77   业务场景
├── test_security.py         ← API-82~87   业务安全
├── requirements.txt
└── README.md
```

> **为什么按"接口动作"分文件，不按"用例分组"分**：一个文件坏了能立刻定位到是哪个接口的问题；编号顺序和设计文档一一对应，方便对表填结果。

### 4.2 怎么跑

```bash
cd automation

# 第一次：装依赖（只需一次）
pip install -r requirements.txt

# 跑全部
pytest -v
```

**期望输出（末尾）**：

```
============================= 89 passed in 16.15s ==============================
```

**`89` 和设计文档里的 `87` 对不上？** 因为有用例用了参数化（一条用例展开成多条），比如 `API-05` 会让三个角色各跑一次、`API-37~40` 会展开成 4 条。**参数化展开后的条数 = pytest 统计的条数**，这是正常的，不是写错了。

### 4.3 只看某几组用例

```bash
pytest -v test_issue_update.py                     # 只跑"更新"这一个文件
pytest -v -k "api_47 or api_49"                    # 只跑含 api_47 或 api_49 的用例
pytest -v -k "negative"                            # 只跑名字含 negative 的（反向用例）
pytest -v --collect-only                           # 不执行，只列出所有用例名（对表用）
```

### 4.4 生成 HTML 报告

```bash
pip install pytest-html
pytest --html=report.html --self-contained-html
```

跑完在 `api_tests` 目录下生成 `report.html`，浏览器打开就是一份带通过/失败统计的测试报告。

### 4.5 代码逐层看一遍（知道每层在干嘛）

#### ① `config.py` —— 配置层

```python
BASE_URL = "http://localhost:3000"          # 换环境只改这里
KEYS = {"admin": "...", "reporter1": "...", ...}   # 各角色的 Key
PROJECT_ID = 1
STATUS_CLOSED = 5                            # 用名字代替魔法数字
```

> **为什么要给状态码起名字**：用例里写 `status_id=STATUS_CLOSED` 比写 `status_id=5` 可读得多，而且数据库里状态 id 变了只改这一行。

#### ② `api_client.py` —— 接口封装层

```python
class RedmineAPI:
    def create_issue(self, **fields):        # 一个方法 = 一个接口
        return self._request("POST", "/issues.json", json_body={"issue": fields})

    def read_field(self, issue_id, *path):   # ★ 回读：接口测试的核心动作
        resp = self.get_issue(issue_id)
        value = resp.json()["issue"]
        for key in path:
            value = value[key]
        return value                          # read_field(3, "status", "name") → "New"
```

> **`**fields`（术语：关键字参数打包）**：把调用时写的 `subject="x", priority_id=3` 收成一个字典 `{"subject": "x", "priority_id": 3}`，这样加字段不用改方法签名。
> **`read_field` 为什么要单独封装**：因为"改完再读一次"这个动作，在越权/状态机用例里要用几十遍，封装后一行就能完成。

#### ③ `conftest.py` —— 测试夹具（fixture）

```python
@pytest.fixture
def temp_issue(admin):
    """创建临时 Issue，测试结束自动删除"""
    created = []
    def make(**fields):
        iid = admin.create_issue_or_fail(**fields)
        created.append(iid)
        return iid
    yield make                    # ← yield 之前是"准备"，之后是"清理"
    for iid in created:
        admin.delete_issue(iid)
```

> **fixture（固件/夹具，术语）**：pytest 的"公共准备工作"。
> 写成测试函数的参数名，pytest 就会自动帮你调用它，并在测试结束后执行 `yield` 后面的清理代码。
> **它的价值**：`temp_issue` 让 30 多个用例都能"创建一个干净数据、用完自动删掉"，而不用每个用例自己写一遍创建和清理。

#### ④ `test_*.py` —— 用例层

```python
def test_api_47_illegal_transition_blocked(developer, temp_issue, unique):
    """API-47【反向-功能异常 P1】developer1 从 New 跳到 Closed 应当被工作流拦住"""
    iid = temp_issue(subject=f"API-47 非法转移-{unique}")

    resp = developer.update_issue(iid, status_id=STATUS_CLOSED)
    assert resp.status_code == 204                    # 接口说"成功"了

    after = developer.read_field(iid, "status", "name")
    assert after == "New"                             # ← 但数据没变，这才说明拦住了
```

> **用例层的写法特点**：**只写业务断言，不写 HTTP 细节**。
> 路径拼接、请求头、JSON 包装都被 `api_client.py` 吃掉了，所以读起来像在描述测试意图。

### 4.6 怎么加一条自己的用例

```python
def test_api_88_my_case(admin, temp_issue, unique):
    """API-88【自己写的】描述预期"""
    iid = temp_issue(subject=f"API-88 测试-{unique}")
    resp = admin.update_issue(iid, priority_id=4)
    assert resp.status_code == 204
    assert admin.read_field(iid, "priority", "name") == "Urgent"
```

三步：**用 fixture 拿数据 → 调封装好的接口方法 → 断言 + 回读**。不用管 HTTP 细节。

## 第五章 结果记录

### 5.1 自动化执行记录（推荐主用）

一条命令跑完，结果就是记录：

```bash
cd automation
pytest --html=report.html --self-contained-html
```

**产物**：`report.html` —— 截图/导出这一份，就是"接口测试执行结果"的凭证。

### 5.2 手工核对记录表（需要人工判断的项）

### 5.3 记录的三条纪律

1. **「设计」和「执行」分开写**。设计 87 条是事实；**通过率、缺陷数必须跑完才有**。
2. **自动化的条数如实报**（pytest 说 89 passed 就是 89），别自己换算成"87 条"去凑设计文档 —— 参数化展开是正常现象。
3. **发现"不一致"要分清是缺陷还是设计**。比如 API-83（匿名可读 issues/projects）是 Redmine 的设计，**不是漏洞**；而 API-22/23（无效枚举值静默回落）**是真的不一致**。两者别混着报。

## 第六章 常见报错排查

### 6.1 接口层

| 现象 | 真实原因 | 解决 |
|---|---|---|
| **所有请求都 403，且响应体是空的** | **REST API 没启用** | 管理→设置→API→勾选「启用 REST Web Service」；或跑 `setup-api-env.cmd` |
| 所有请求 401 | Key 错 / 没带 `X-Redmine-API-Key` 头 | 用「我的账号」里的 Key；确认请求头名拼写正确（是 `X-Redmine-API-Key`） |
| Key 换了但脚本还用旧的 | `config.py` 没更新 | 改 `automation/config.py` 的 `KEYS` |
| 创建返回 422 | 缺必填字段或值非法 | **看响应体的 `errors` 数组** —— Redmine 会写明哪里不对，例：`{"errors":["Subject cannot be blank"]}` |
| 403 但 Key 是对的 | 该角色没这个权限 | 查设计文档 2.3 的字段表 / 用 admin 对照测一次 |
| **PUT 返回 204 但数据没变** | **无权限 或 状态转移不合法**（Redmine 静默忽略） | **这是预期行为，不是 bug** —— 用例要按"未生效"断言 |
| 返回 404 | 路径拼错 或 id 不存在 | 检查路径；`GET /issues/{id}.json` 的 id 是否真实存在 |
| 中文变乱码 | 编码没指定 | 请求头加 `charset=utf-8`，请求体用 UTF-8 编码 |
| 过滤不存在的 project 返回 404 | 这是 Redmine 的实际行为 | 不是 bug（见设计文档 API-69） |

### 6.2 pytest 层

| 现象 | 原因 | 解决 |
|---|---|---|
| `ModuleNotFoundError: No module named 'requests'` | 没装依赖 | `pip install -r requirements.txt` |
| `ModuleNotFoundError: No module named 'api_client'` | 没在 `api_tests` 目录下跑 | `cd` 到 `api_tests` 再跑 pytest |
| 大量用例 401 | `config.py` 里的 Key 是旧的 | 重跑 `setup-api-env.cmd` 拿新 Key，填进 `config.py` |
| **大量用例 403** | **REST API 没启用** | 同 6.1 第一条 |
| API-05 失败，报"竟然能列用户" | 权限配错了 | 检查三个角色是否真的没有管理员权限 |
| API-47/49 失败，报"非法转移生效了" | **工作流没配好** | 跑 `seed-workflow.rb` 重配工作流（见 `docs/2.2-环境搭建指南.md` 第五章） |
| 跑完库里多了一堆 Issue | 某条用例没清理干净 | 检查用例是否用了 `temp_issue`；已删除的会 404，可忽略 |
| 用例单独跑过、一起跑失败 | 用例之间有数据依赖 | 检查是否用了 `unique` fixture 生成唯一标题 |

### 6.3 环境层

| 现象 | 原因 | 解决 |
|---|---|---|
| `docker ps` 报连不上 daemon | Docker Desktop 没启动 | 启动 Docker Desktop，等托盘图标变绿 |
| 连不上 `localhost:3000` | 容器没起 | 跑 `scripts/start-redmine.cmd` |
| 容器起了但页面 500 | 默认数据没加载 | 见 `docs/2.2-环境搭建指南.md` 第一章 |
| `docker exec` 报 `Cwd must be an absolute path` | Git Bash 把容器路径当本地路径转换了 | `export MSYS_NO_PATHCONV=1` |
| `rails runner` 报 `Missing secret_key_base` | 容器只给了 `REDMINE_SECRET_KEY_BASE` | 用 `run-seed.sh` 包装（它做了显式转换） |
