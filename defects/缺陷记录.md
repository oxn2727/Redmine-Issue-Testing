# 缺陷记录

> **两条纪律**：① 一条缺陷一行，**边跑边记**，跑完一条立刻填，禁止事后凭回忆补 —— 靠回忆填出来的缺陷单，被问一句复现步骤就露馅；② **没跑出来的缺陷不写**。

---

## 一、提报规范

一条合格的缺陷必须能**被另一个人独立复现**，因此以下四要素缺一不可。

| 字段 | 要求 | 反例 |
|---|---|---|
| **标题** | 一句话说清「在哪 + 什么条件 + 什么现象」 | ❌「创建有问题」 |
| **环境** | 版本 / 账号 / 数据前置（如某项目内、某角色登录） | ❌「本地」 |
| **复现步骤** | 编号步骤，一步一个动作；接口类附**完整请求**（方法 + URL + 请求头 + 请求体） | ❌「调接口报错」 |
| **期望 vs 实际** | 分开写；接口类附**完整响应**（状态码 + 响应体） | ❌「结果不对」 |

> **界面类**：附操作路径（如 `项目 → Issues → New issue`）与截图。
> **接口类**：请求体给**能原样发送的 JSON**，不给「xx字段=xx」这种碎片 —— 碎片等于没写。

---

## 二、严重程度定义

| 级别 | 定义 | 例子 |
|---|---|---|
| **S1 致命** | 数据丢失 / 越权真的成功（本该拦住却改了数据）/ 系统不可用 | 低权限用户真的改掉了他人 Issue |
| **S2 严重** | 主流程走不通，且无绕过方式 | 创建 Issue 必然失败 |
| **S3 一般** | 非主流程功能异常、校验缺失但有替代路径 | 日期倒挂未拦截 |
| **S4 轻微** | 文案 / 样式 / 易用性问题 | 提示语错别字 |
