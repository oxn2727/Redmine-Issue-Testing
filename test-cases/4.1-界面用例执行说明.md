# 界面用例执行说明（Issue 模块）

> **这是「怎么做」的执行手册。** 用例本体在 `test-cases/3.2-界面用例-Issue模块-69条.md`，这里只讲**怎么把它跑完、怎么记、怎么提缺陷**。
>   
> 接口侧的执行见 `automation/4.2-接口测试执行步骤.md`。



---

## 一、跑之前先确认三件事

|  #  | 事项                 | 怎么确认                                                   | 不满足会怎样                                               |
| :-: | ------------------ | ------------------------------------------------------ | ---------------------------------------------------- |
|  1  | **环境能登录**          | 浏览器打开 `http://localhost:3000`，用 `admin / Test@1234` 登入 | 后面全是白测 —— 先走 `docs/2.2-环境搭建指南.md`                        |
|  2  | **界面语言 = English** | 右上角 My account → Language 应为 `English`                 | ⚠️ 用例里的预期提示语是英文原文（`Subject cannot be blank`…），切中文对不上 |
|  3  | **冒烟全绿**           | 先跑 `test-cases/3.1-冒烟用例.md` 的 17 条界面冒烟                            | 带病跑完整用例，几十条失败全是环境噪声，白费时间                             |

**界面层是手工执行**（本项目不做 UI 自动化）。所以对执行者的唯一要求是：**按用例步骤走，逐条填「实际结果」**。

---

## 二、推荐执行顺序（按账号分组，别按文档顺序跳着跑）

用例表的顺序是**按功能点**排的，但执行时**按账号分组**效率高得多 —— 否则你会不停在四个账号之间登录登出。

```
① admin       预置数据（建 #A #B、建第 2 个项目 v2-0、接口预置 1 条私有 Issue）
      ↓
② reporter1   F1 创建 → F2 查看 → F8 工时 → F10 列表视图 → F11 搜索 → F12 批量 → F13 导出
      ↓
③ developer1  F3 编辑 → F4 复制/移动 → F5 关联 → F6 子任务 → F7 附件 → S 组（S-01/02/04/05/06/07/08/09）
      ↓
④ manager1    F4-01 删除 → F9 关注者 → S-03 → P-07/P-08/P-09 的写方
      ↓
⑤ 无痕窗口      P-05 匿名访问
```

> **为什么 admin 只在①出场**：admin 是超管，能删任何单、能直接改状态 —— 用它跑 S 组 / P 组，结论全部失真。**它只负责预置。**
>   
> 每条用例的「前置条件」列已写清该用哪个账号，**以上分组只是把它归了堆**。

## 三、怎么记录

**一条用例只有一个「实际结果」格 —— 直接填在用例表最后一列，不要另建表。**

| 情形         | 填什么                                                |
| ---------- | -------------------------------------------------- |
| 跑通了        | `通过`（有值得记的现象就补一句，如 `通过（提示语为 xxx）`）                 |
| 跑了但结果和预期不符 | `失败：实际 <现象>` —— **现象写具体**（截图存 `截图/` 目录，文件名 = 用例编号） |
| 还没跑        | 保持 `待执行`                                           |

**通过率怎么算**：`已通过的用例数 ÷ 已执行的用例数`。

- **分母是"已执行"，不是 69** —— 没跑的不能算失败，也不能算通过。
- **分母是"用例条数"，不是"取值点数量"** —— 界面 33 个取值点、接口 87 组参数**只用于核对覆盖有没有漏**。
- 报数字时分开说：`界面层 69 条，已执行 X 条，通过 Y 条`。

## 四、发现缺陷怎么提

缺陷记录统一维护在 `defects/` 下，一条缺陷一行：

| 字段           | 写什么            |
| ------------ | -------------- |
| **用例编号**     | 如 `F1-10`      |
| **复现步骤**     | ①②③，别人照着能复现    |
| **实际 vs 预期** | 一行对照，别只写"不对"   |
| **截图路径**     | `截图/F1-10.png` |
| **严重程度**     | 见下表            |

**严重程度怎么定**（不要所有缺陷都写"严重"）：

|   级别   | 判据                     | 例                             |
| :----: | ---------------------- | ----------------------------- |
| **严重** | 主流程走不通 / 数据被改坏 / 越权能成功 | 无权限的 reporter1 真把别人的 Issue 改了 |
| **一般** | 功能可用但有错误：校验漏了、值算错、状态不对 | 附件超 5MB 竟然传上去了                |
| **轻微** | 界面/文案问题，不影响功能          | 提示语里少个空格、日期显示格式不统一            |

> **提缺陷的三条纪律**：① **先排除环境**（换账号/清缓存/重启容器后还在，才算）② **一条用例一个缺陷**，别把三个问题写在一条里 ③ **"设计如此"不算缺陷** —— 比如匿名能读 `/issues.json` 是 Redmine 的设计意图，报它是新手最容易犯的错。

## 五、执行完手上有什么

| 产物           | 在哪                           |
| ------------ | ---------------------------- |
| 填好「实际结果」的用例表 | `test-cases/3.2-界面用例-Issue模块-69条.md` |
| 冒烟自检记录       | `test-cases/3.1-冒烟用例.md`                |
| 缺陷清单         | `defects/缺陷记录.md`（新建）                |
| 截图           | `截图/`（新建）                    |
| 通过率数字        | 按上文口径自己算                     |

> **记录红线**：**设计了 69 条界面用例**是事实，可以写；**通过率 / 缺陷数必须跑完才有** —— 没跑完就写"通过率 95%"是编造，被追问一句"哪个用例失败的、为什么"就穿帮了。
>   
> **数字口径不一致时不要"圆"，直接讲版本迭代**："初版设计 148 条，复盘后把界面层细分到 156 条。" 这说明用例集在迭代，是加分项。
