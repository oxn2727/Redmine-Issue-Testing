### 0.2 每个请求都要带的请求头

| 方法 | 请求头 |
|---|---|
| GET / DELETE | `X-Redmine-API-Key: <该账号的 Key>` |
| POST / PUT | `X-Redmine-API-Key: <该账号的 Key>`<br>`Content-Type: application/json` |

> **两个都必须显式写**：
> ① 认证靠 `X-Redmine-API-Key`（不用账号密码、不用 Cookie）。
> ② **POST / PUT 必须带 `Content-Type: application/json`** —— 官方原文「MUST be specified even if the remote URL is suffixed accordingly」，URL 带 `.json` 后缀也**必须**设，否则服务端解析不了 body。
> ③ 前置开关：**管理 → 设置 → API → 勾选「启用 REST Web Service」**，不勾则**所有**接口返回 403 且响应体为空。

### 0.3 本环境固定数据（id 对照表）

| 对象 | 取值 |
|---|---|
| 项目 | `project_id = 1`（电商后台 V1.0） |
| 跟踪标签 | `1=Bug`　`2=Feature`　`3=Support` |
| 状态 | `1=New`　`2=In Progress`　`3=Resolved`　`4=Feedback`　`5=Closed`　`6=Rejected` |
| 优先级 | `1=Low`　`2=Normal`　`3=High`　`4=Urgent`　`5=Immediate` |
| 问题类别 | `1=前端`　`2=后端`　`3=数据库` |
| 目标版本 | `1=V1.1`　`2=V2.0` |
| 用户 | `1=admin` |
| **不存在的 id** | `999999`（专用于"资源不存在"用例） |

### 0.4 用例怎么读

- **一条用例 = 一个接口请求 = 一个可独立填写的「实测」格**。正向/反向分组只影响**设计方法**，不影响"一条一行"。
- 「请求数据」列写的就是**可以原样复制发送的完整 body**，不是缩写、不是"某字段=某值"的碎片。
- **`<id>`** 表示"前面某一步创建出来的 Issue 编号"，执行时替换成真实数字。
- PUT / DELETE 类用例的「预期结果」都带一句**回读要求** —— Redmine 的 204 不可信（见 0.5）。

### 0.5 状态码与通用响应体约定（下文不再重复写）

| 码 | 通用响应体 | 说明 |
|:--:|---|---|
| **200** | 各条单独给 | 查询 / 列表成功，有内容 |
| **201** | 各条单独给 | 创建成功，返回新对象（含 `id`） |
| **204** | **无响应体** | **更新 / 删除成功（⚠️ 不是 200）** |
| **400** | 空 | 请求体不是合法 JSON（服务器读不懂） |
| **401** | **空** | Key 错误 / 缺失 |
| **403** | 空 | 无权限；或 REST API 未启用 |
| **404** | 空 | 资源不存在 |
| **422** | `{"errors": ["<具体原因>"]}` | 字段值非法；**断言时应校验 `errors` 内容** |

> **⚠️ 全文档最重要的一条**：**PUT / DELETE 成功返回 204，但不是 200；而且 204 不代表改成功** —— 无权限、非法状态转移时 Redmine 也返回 204，但数据**原封不动**。
> → **凡 PUT / DELETE 用例，必须"改完再 GET 一次"回读验证**（下文相关用例的「预期结果」都写了这一步）。

## 一、单接口用例（API-01 ~ API-69）

### 1.1 认证　`GET {{BASE}}/users/current.json`、`GET {{BASE}}/users.json`

**公共前置**：REST API 已启用
**公共请求头**：`X-Redmine-API-Key: <key>`（GET 无需 Content-Type）

**curl 模板（复现最直接）**

```bash
# 正确 Key → 200
curl -s -H "X-Redmine-API-Key: $K_ADMIN" $BASE/users/current.json

# 错误 Key → 401（只看状态码）
curl -s -o /dev/null -w "%{http_code}\n" -H "X-Redmine-API-Key: wrong-key-123" $BASE/users/current.json
```

|     编号     | 用例名称      |  优先级   | 前置条件          | 请求                        | 请求头                                                              | 预期结果                           |  实测   |
| :--------: | --------- | :----: | ------------- | ------------------------- | ---------------------------------------------------------------- | ------------------------------ | :---: |
| **API-01** | 正确 Key    | **P0** | admin Key 有效  | `GET /users/current.json` | `X-Redmine-API-Key: <admin>`                                     | **200**，`user.login` = `admin` | ✅ 200 |
|   API-02   | 错误 Key    | **P0** | —             | `GET /users/current.json` | `X-Redmine-API-Key: wrong-key-123`                               | **401**，响应体为空                  | ✅ 401 |
|   API-03   | 缺失 Key 头  | **P0** | —             | `GET /users/current.json` | 不带任何认证头                                                          | **401**                        | ✅ 401 |
|   API-04   | Key 格式非法  |   P2   | —             | `GET /users/current.json` | `X-Redmine-API-Key: abc`（3 字符）                                   | **401**                        | ✅ 401 |
| **API-05** | 越权访问管理员接口 | **P1** | 用三个低权限角色的 Key | `GET /users.json`         | `X-Redmine-API-Key: <reporter1>` / `<developer1>` / `<manager1>` | **403**（三个角色都是）                | ✅ 403 |
| API-05·对照  | 管理员访问同一接口 |   P1   | admin Key     | `GET /users.json`         | `X-Redmine-API-Key: <admin>`                                     | **200**，返回 `users` 数组          | ✅ 200 |

**API-01 预期响应（200）**

```json
{"user":{"id":1,"login":"admin","admin":true,"firstname":"Redmine","lastname":"Admin","mail":"...","created_on":"...","api_key":"..."}}
```

> **API-05 是接口测试最有价值的一条**：界面上普通用户看不到「管理」菜单，但**接口不藏**。用低权限 Key 直接打 `/users.json` → 403，说明后端**独立做了权限校验**，不是靠前端藏菜单。
> **对照组（admin → 200）必须同时测**：只测 403 分不清"权限拦住了"还是"接口本身坏了"。

### 1.2 创建 Issue · 正向　`POST {{BASE}}/issues.json`

**公共前置**：REST API 已启用；`project_id=1` 存在
**公共请求头**：`X-Redmine-API-Key: <admin>`　＋　`Content-Type: application/json`

**curl 模板**

```bash
curl -s -X POST -H "X-Redmine-API-Key: $K_ADMIN" -H "Content-Type: application/json" \
  -d '{"issue":{"project_id":1,"subject":"API-06 必选参数"}}' \
  $BASE/issues.json
```

| 编号 | 用例名称 | 优先级 | 前置条件 | 请求数据（完整可发送） | 预期结果 | 实测 |
|:---:|---|:---:|---|---|---|:---:|
| **API-06** | 必选参数 | **P0** | 无（只需项目存在） | `{"issue":{"project_id":1,"subject":"API-06 必选参数"}}` | **201**；返回 `issue.id`；未传字段取默认（`status`=New、`tracker`=Bug） | ✅ 201 |
| API-07 | 组合参数 | P2 | 无 | `{"issue":{"project_id":1,"subject":"API-07 组合参数","tracker_id":2,"priority_id":3,"description":"组合参数用例"}}` | **201**；`tracker`=Feature、`priority`=High、`description` 原样回显 | ✅ 201 |
| **API-08** | 全部参数 | P1 | **先创建一条父任务**，拿到它的 `<id>` | 见下方「API-08 完整请求体」 | **201**；下方 8 个字段全部按传入值回显 | ✅ 201 |

**API-08 完整请求体**（照这个发）

```json
{
  "issue": {
    "project_id": 1,
    "subject": "API-08 全部参数",
    "tracker_id": 1,
    "status_id": 1,
    "priority_id": 3,
    "description": "全部可选字段都传",
    "assigned_to_id": 1,
    "category_id": 1,
    "fixed_version_id": 1,
    "parent_issue_id": 101,
    "start_date": "2026-09-24",
    "due_date": "2026-10-08",
    "estimated_hours": 8.5,
    "done_ratio": 30,
    "is_private": false
  }
}
```

**回读断言（GET /issues/<id>.json）**

```
category.name == "前端"      fixed_version.name == "V1.1"      parent.id == <父任务 id>
start_date == "2026-09-24"   due_date == "2026-10-08"
estimated_hours == 8.5       done_ratio == 30                  is_private == false
```

> **API-08 的「前置条件」为什么必须写**：`parent_issue_id` / `category_id` / `fixed_version_id` / `assigned_to_id` 指向的对象**都必须先存在**，否则这条用例会返回 422（引用不存在的资源）。这就是"**用较少的用例覆盖更多的接口**"的思路 —— 一条全部参数用例，实际把 4 个关联关系全验了一遍。

### 1.4 创建 Issue · 反向之「数据异常」　`POST {{BASE}}/issues.json`

**定义**：数据类型 / 格式 / 长度 / 范围**不对**，用 **等价类 + 边界值** 设计。
**公共前置 / 请求头**：同 1.2。

| 编号 | 用例名称 | 设计方法 | 优先级 | 请求数据（完整可发送） | 预期结果 | 实测 |
|:---:|---|---|:---:|---|---|:---:|
| API-15 | subject 为空串 | 等价类（无效） | P1 | `{"issue":{"project_id":1,"subject":""}}` | **422** | ✅ 422 |
| API-16 | subject 为纯空格 | 等价类（无效） | P2 | `{"issue":{"project_id":1,"subject":"   "}}` | **422** | ✅ 422 |
| **API-17** | subject = 255 字符 | **边界值（上边界内）** | P1 | `{"issue":{"project_id":1,"subject":"<255 个 c>"}}` | **201** | ✅ 201 |
| **API-18** | subject = 256 字符 | **边界值（上边界外）** | P1 | `{"issue":{"project_id":1,"subject":"<256 个 b>"}}` | **422** | ✅ 422 |
| API-19 | subject 超长 300 字符 | 边界值（远超） | P2 | `{"issue":{"project_id":1,"subject":"<300 个字>"}}` | **422** | ✅ 422 |
| API-20 | project_id 传字符串 | 等价类（类型错） | P2 | `{"issue":{"project_id":"abc","subject":"类型错"}}` | **422** | ✅ 422 |
| API-21 | 优先级不存在 | 等价类（无效） | P1 | `{"issue":{"project_id":1,"subject":"坏优先级","priority_id":999}}` | **422** | ✅ 422 |
| **API-22** | **状态不存在（陷阱）** | 等价类（无效） | P1 | `{"issue":{"project_id":1,"subject":"API-22 非法状态","status_id":999}}` | ⚠️ **201**，且状态**静默回落为 New** | ⚠️ 201 → New |
| **API-23** | **跟踪标签不存在（陷阱）** | 等价类（无效） | P1 | `{"issue":{"project_id":1,"subject":"API-23 非法跟踪","tracker_id":999}}` | ⚠️ **201**，且标签**静默回落为 Bug** | ⚠️ 201 → Bug |
| API-24 | 完成度 = 101 | 边界值（上边界外） | P1 | `{"issue":{"project_id":1,"subject":"越界进度","done_ratio":101}}` | **422** | ✅ 422 |
| API-25 | 完成度 = -5 | 边界值（下边界外） | P2 | `{"issue":{"project_id":1,"subject":"负进度","done_ratio":-5}}` | **422** | ✅ 422 |
| API-26 | 完成度 = 0 / 100 | 边界值（上下边界内） | P2 | `{"issue":{"project_id":1,"subject":"进度边界","done_ratio":0}}`　／　`...,"done_ratio":100` （两个值各发一次） | **201**，两者都成功且回读 `done_ratio` 等于传入值 | ✅ 201 |
| API-27 | 预估工时 = -1 | 边界值（下边界外） | P2 | `{"issue":{"project_id":1,"subject":"负工时","estimated_hours":-1}}` | **422** | ✅ 422 |
| API-28 | 日期格式非法 | 等价类（格式错） | P2 | `{"issue":{"project_id":1,"subject":"坏日期","start_date":"2026-13-45"}}`　／　`...,"due_date":"not-a-date"` （两个字段各发一次） | **422** | ✅ 422 |

**API-22 / API-23 的构造方式**（这两条要回读，不能只看状态码）

```bash
# 创建（返回 201）
curl -s -X POST -H "X-Redmine-API-Key: $K_ADMIN" -H "Content-Type: application/json" \
  -d '{"issue":{"project_id":1,"subject":"API-22 非法状态","status_id":999}}' $BASE/issues.json
# → 记下 issue.id，然后回读 status.name；期望是 "New"（不是 999，也不是报错）
curl -s -H "X-Redmine-API-Key: $K_ADMIN" $BASE/issues/<id>.json
```

> **🔴 API-22 / API-23 是本节最值钱的两条**（官方文档不会写）：

| 字段 | 传不存在的 id | 接口返回 | 实际存了什么 |
|---|---|---|---|
| `priority_id=999` | **422 报错** | 拒绝了 |
| `status_id=999` | **201 成功** | **静默替换成默认状态 New** |
| `tracker_id=999` | **201 成功** | **静默替换成默认标签 Bug** |

> **同一个接口，三个相似字段，三种处理方式** —— 典型的**接口设计不一致**，调用方无法感知参数被丢弃。（详见 `2.5` 第四章）

### 1.5 创建 Issue · 反向之「参数异常」　`POST {{BASE}}/issues.json`

**定义**：参数的**结构**不对（不是值不对）。
**公共前置 / 请求头**：同 1.2。

| 编号 | 小类 | 优先级 | 请求数据（完整可发送） | 预期结果 | 实测 |
|:---:|---|:---:|---|---|:---:|
| API-29 | **无参** | P2 | `{}` | **422** | ✅ 422 |
| API-29B | **数据异常（格式错）** | P2 | 请求体**不是合法 JSON**：`{bad json`（注意：用 `data=` 原样发，不要用 `json=`） | **400**（不是 422！） | ✅ 400 |
| API-30 | **少参** | P2 | `{"issue":{"subject":"只有主题"}}`（缺 `project_id`） | **422** | ✅ 422 |
| API-31 | **少参** | P2 | `{"issue":{"project_id":1}}`（缺 `subject`） | **422** | ✅ 422 |
| API-32 | **错误参数名** | P2 | `{"issue":{"project_id":1,"subjct":"拼错"}}`（少一个 e） | **422** | ✅ 422 |
| API-33 | **错误参数名** | P2 | `{"issue":{"projectId":1,"subject":"驼峰"}}`（驼峰，正确是下划线） | **422** | ✅ 422 |
| API-34 | **结构错** | P2 | `{"project_id":1,"subject":"没包 issue"}`（字段直接放顶层，未包 `issue`） | **422** | ✅ 422 |
| API-35 | **多参** | P3 | `{"issue":{"project_id":1,"subject":"多余字段","__bogus__":"x"}}` | **201（多余字段被忽略）** | ✅ 201 |

**API-29B 的 curl（注意：不能带 `Content-Type: application/json`）**

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST \
  -H "X-Redmine-API-Key: $K_ADMIN" \
  -d '{bad json' $BASE/issues.json
```

> **API-29B 的价值：400 和 422 是两种错误，别混**
> **400 Bad Request** = 请求本身不合法（JSON 都解析不了，服务器读不懂你说的什么）
> **422 Unprocessable Entity** = 请求格式没问题，但**字段值不合法**（读懂了，内容不对）
> 混为一谈就无法区分"客户端发错了"和"服务端校验不过"。

> **API-35 的预期是"成功"**：多传未知字段被忽略是**合理的向前兼容**。**参数异常类用例的预期不是一律报错** —— 分不清这点，就会把正确行为误报成缺陷。

### 1.6 查询 Issue 详情　`GET {{BASE}}/issues/<id>.json`

**公共前置**：`<id>` 为一条已存在的 Issue（先用 API-06 建一条）
**公共请求头**：`X-Redmine-API-Key: <admin>`

**curl 模板**

curl -s -H "X-Redmine-API-Key: $K_ADMIN" $BASE/issues/<id>.json
```

| 编号 | 用例名称 | 类别 | 优先级 | 请求 | 预期结果 | 实测 |
|:---:|---|---|:---:|---|---|:---:|
| **API-36** | 查询存在的 Issue | 正向-必选 | **P0** | `GET /issues/<id>.json` | **200**，含 `id / project / tracker / status / priority / author / subject / created_on / updated_on` | ✅ 200 |
| API-37 | 查询不存在的 Issue | 反向-功能异常 | P1 | `GET /issues/999999.json` | **404** | ✅ 404 |

| API-39 | id 传 0 | 反向-边界值 | P2 | `GET /issues/0.json` | **404** | ✅ 404 |
| API-40 | id 传负数 | 反向-边界值 | P3 | `GET /issues/-1.json` | **404** | ✅ 404 |
| API-41 | 带 include 参数 | 正向-组合 | P2 | `GET /issues/<id>.json?include=journals` | **200**，响应多出 `journals` 子对象 | ✅ 200 |
| API-42 | 用 XML 格式取 | 正向-组合 | P3 | `GET /issues/<id>.xml` | **200**，响应体以 `<?xml` 开头 | ✅ 200 |

> **API-37/38/39/40 是同一个等价类（id 无效）的四个代表值** —— 不存在、非数字、0、负数。四个都返回 **404** 说明**处理一致**；若有一个返回 500，那就是缺陷。

### 1.7 更新 Issue　`PUT {{BASE}}/issues/<id>.json`

**公共前置**：`<id>` 为一条已存在的 Issue
**公共请求头**：`X-Redmine-API-Key: <key>`　＋　`Content-Type: application/json`

**curl 模板（★ 带回读）**

# 改（成功返回 204，无响应体）

```

| 编号 | 用例名称 | 类别 | 优先级 | 用哪个 Key | 请求数据（完整可发送） | 预期结果 | 实测 |
|:---:|---|---|:---:|---|---|---|:---:|
| **API-43** | 改标题 | 正向-必选 | **P0** | `<admin>` | `{"issue":{"subject":"API-43 改之后"}}` | **204**，回读 `subject` = "API-43 改之后" | ✅ 204 生效 |
| API-44 | 加注释 | 正向-组合 | P1 | `<admin>` | `{"issue":{"notes":"这是一条接口测试注释"}}` | **204**，回读 `?include=journals` 里能找到该注释 | ✅ 204 入库 |
| API-45 | 合法状态转移 New→In Progress | 正向-组合 | P1 | `<developer1>` | `{"issue":{"status_id":2}}` | **204**，回读 `status.name` = "In Progress" | ✅ 204 生效 |
| API-46 | 一次改多个字段 | 正向-全部 | P1 | `<admin>` | `{"issue":{"subject":"API-46 改完","priority_id":3,"due_date":"2026-12-31"}}` | **204**，回读三个字段都变 | ✅ 204 生效 |

| API-48 | 改他人的 Issue（有权限） | 正向 | P1 | `<developer1>` | `{"issue":{"subject":"API-48 被 developer 改了"}}`（目标是 **admin 提的** Issue） | **204**，回读标题已变（Developer 有 `edit_issues`） | ✅ 204 生效 |
| **API-49** | **改他人的 Issue（无权限）** | **反向-越权** | **P1** | `<reporter1>` | `{"issue":{"subject":"reporter1 篡改的标题"}}`（目标是 **admin 提的** Issue） | **204，但回读标题未变**（Reporter 无 `edit_issues`） | ⚠️ 204 **未生效** |
| API-50 | 改自己的 Issue（无权限角色） | 正向-越权边界 | P1 | `<reporter1>` | `{"issue":{"subject":"API-50 reporter 自己改了"}}`（目标是 **reporter1 自己提的**） | **204**，回读标题已变（有 `edit_own_issues`） | ✅ 204 生效 |
| API-51 | 更新不存在的 Issue | 反向-功能异常 | P1 | `<admin>` | `PUT /issues/999999.json`，body `{"issue":{"subject":"不存在"}}` | **404** | ✅ 404 |
| API-52 | 改为空 subject | 反向-数据异常 | P1 | `<admin>` | `{"issue":{"subject":""}}` | **422** | ✅ 422 |
| API-53 | 改 done_ratio 越界 | 反向-数据异常 | P2 | `<admin>` | `{"issue":{"done_ratio":200}}` | **422** | ✅ 422 |
| API-54 | 空 body | 反向-参数异常（无参） | P3 | `<admin>` | `{}` | **204**（无字段可改，视为幂等成功） | ✅ 204 |
| API-55 | body 带未知字段 | 反向-参数异常（多参） | P3 | `<admin>` | `{"issue":{"__bogus__":"x"}}` | **204**（多余字段被忽略），且未改坏其它字段 | ✅ 204 |

> **🔴 API-47 / API-49 是接口测试存在的意义**：

| | 界面上的现象 | 接口上的现象 |
|---|---|---|
| 非法状态转移 | 下拉框里**根本没有 Closed 选项**（前端藏了） | **接口返回 204，看起来"成功"了** |
| 无权限改他人 | 没有「编辑」按钮（前端藏了） | **接口返回 204，看起来"成功"了** |

> 只测界面，你会以为"前端限制了就行"。**接口返回 204 但回读数据没变，才说明后端也真的防住了**（后端二次校验）。
> 反过来，如果回读发现**数据真被改了** → **高危越权漏洞**。**只看状态码，这两种情况长得一模一样。**

### 1.8 删除 Issue　`DELETE {{BASE}}/issues/<id>.json`

**公共前置**：`<id>` 为一条已存在的 Issue
**公共请求头**：`X-Redmine-API-Key: <key>`

**curl 模板（带回读）**

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X DELETE -H "X-Redmine-API-Key: $K_ADMIN" $BASE/issues/<id>.json
curl -s -o /dev/null -w "%{http_code}\n" -H "X-Redmine-API-Key: $K_ADMIN" $BASE/issues/<id>.json   # 期望 404
```

| 编号 | 用例名称 | 类别 | 优先级 | 用哪个 Key | 请求 | 预期结果 | 实测 |
|:---:|---|---|:---:|---|---|---|:---:|
| **API-56** | 删除存在的 Issue | 正向-必选 | **P0** | `<admin>` | `DELETE /issues/<id>.json` | **204**，之后 `GET` 返回 **404** | ✅ 204 |
| API-57 | 删除不存在的 Issue | 反向-功能异常 | P1 | `<admin>` | `DELETE /issues/999999.json` | **404** | ✅ 404 |
| API-58 | 重复删除（幂等性） | 反向-功能异常 | P2 | `<admin>` | 删除成功后**再删一次**同一 `<id>` | **404** | ✅ 404 |
| **API-59** | **普通用户删他人的** | **反向-越权** | **P1** | `<reporter1>` | `DELETE /issues/<admin 提的 id>.json` | **403** | ✅ 403 |
| API-60 | 普通用户删自己的 | 反向-越权 | P1 | `<reporter1>` | `DELETE /issues/<reporter1 自己提的 id>.json` | **403**（Reporter 无 `delete_issues`） | ✅ 403 |
| API-61 | 用 GET 访问删除接口 | 反向-数据异常 | P3 | `<admin>` | `GET /issues/<id>.json`（想删却用错方法） | **200**（只读，不会删） | ✅ 200 |

> **API-59 与 API-49 的差异，是理解 Redmine 权限设计的关键**：

| 操作 | 无权时返回 | 为什么不同 |
|---|---|---|
| **改**（PUT） | **204**，静默不改 | 用 `safe_attributes` 过滤掉无权字段，请求"成功"但无事发生 |
| **删**（DELETE） | **403**，明确报错 | 删除是独立动作，controller 里显式 `authorize` 拦截 |

> **同一系统、不同操作的"拒绝方式"都不一样** → 所以**接口测试不能只看状态码，必须回读 + 交叉验证**。

## 二、业务场景用例（API-70 ~ API-77）

**前提**：必须**第一节（单接口）全部跑通**才能进这里。
**定义**：按用户实际使用场景，**连续调用多个接口**。**一般只设计正向**（异常已在单接口层覆盖）。
**公共请求头**：`X-Redmine-API-Key: <按步骤换对应角色的 Key>`　＋　POST/PUT 加 `Content-Type: application/json`

| 编号 | 场景名 | 优先级 | 接口调用链 | 预期结果 | 对应真实业务 |
|:---:|---|:---:|---|---|---|
| **API-70** | **缺陷完整生命周期** | **P0** | 创建 → 查询 → 改状态 → 加注释 → 关闭 → 删除 → 再查 | 每步按序 201/200/204，最终 404 | 一个 Bug 从提报到关闭的全过程 |
| API-71 | 开发者修复流程 | P1 | developer1 认领（→In Progress）→ 修完（→Resolved）→ 加修复说明 | 状态依次流转正确 | 开发修 Bug |
| API-72 | 管理者验收流程 | P1 | manager1 把 Resolved → Closed | 状态 = Closed，`closed_on` 有值 | 测试/管理验收关闭 |
| **API-73** | **打回重开流程** | P1 | 创建 → In Progress → Resolved → Feedback（打回）→ In Progress（再修） | 状态可回退 | Bug 没修好被测试打回 |
| **API-74** | **越权场景（跨角色协作）** | **P1** | reporter1 创建 → reporter1 试关闭（失败）→ manager1 关闭（成功） | 前者状态不变，后者 = Closed | 报告者不能自己关单 |
| API-75 | 子任务场景 | P2 | 创建父任务 → 创建子任务（`parent_issue_id`）→ 查子任务 | `child.parent.id` = 父任务 id | 大 Bug 拆成小任务 |
| API-76 | 搜索/过滤场景 | P2 | 建两条 → 把其中一条改成 In Progress → 按状态过滤 | 过滤结果里只含被改的那条 | 测试找自己负责的 Bug |
| API-77 | 数据一致性场景 | P1 | 创建 → 改 3 次标题 → 查历史（`include=journals`） | 最终标题 = 第 3 次的值；journals = 3 条 | 追溯"谁改了状态" |

**API-70 的完整步骤（场景用例的范式 —— 照这个写）**

| 步 | 用哪个 Key | 请求 | 请求数据 | 断言 |
|:--:|---|---|---|---|
| 1 | `<admin>` | `POST /issues.json` | `{"issue":{"project_id":1,"subject":"API-70 生命周期"}}` | **201**，记下 `issue.id` → `<id>` |
| 2 | `<admin>` | `GET /issues/<id>.json` | — | **200**，`status.name` = "New" |
| 3 | `<manager1>` | `PUT /issues/<id>.json` | `{"issue":{"status_id":2}}` | **204**，**回读** `status.name` = "In Progress" |
| 4 | `<manager1>` | `PUT /issues/<id>.json` | `{"issue":{"notes":"已修复，请验证"}}` | **204**，回读 `?include=journals` 里有该注释 |
| 5 | `<manager1>` | `PUT /issues/<id>.json` | `{"issue":{"status_id":5}}` | **204**，回读 `status.is_closed == true`、`closed_on` 非空 |
| 6 | `<admin>` | `DELETE /issues/<id>.json` | — | **204** |
| 7 | `<admin>` | `GET /issues/<id>.json` | — | **404**（证明真的删了） |

> **第 3、5 步为什么用 `manager1`**：`developer1` 没有关闭权限（API-47 已测）。**场景用例里跨角色操作，必须换对应的 Key** —— 这是接口测试比界面测试麻烦的地方，也是它更真实的地方。
> **"连续调用多个接口"的价值**：单接口都对，串起来不一定对。比如"创建返回的 `id`"能不能被后续接口正确传递（`issue.id`）、状态流转跨接口能不能接上。**这就是集成测试**。

## 四、安全测试点（API-82 ~ API-87）

**说明**：只做**业务安全**。攻击安全（木马/病毒/黑客）由专业安全工程师负责，**我们不测**。
**公共请求头**：按各条说明。

| 编号 | 测试点 | 优先级 | 请求 | 预期结果 | 实测 |
|:---:|---|:---:|---|---|:---:|
| **API-82** | 敏感数据是否泄露 | P1 | `GET /users.json`，头 `X-Redmine-API-Key: <admin>` | **200**；响应体里**不含** `password` / `hashed_password` / `salt` / `api_key` / `auth_source` | ✅ 无密码字段 |
| **API-83** | 未授权访问 | **P0** | **不带任何 Key**，分别 `GET /issues.json`、`/projects.json`、`/users.json`、`/time_entries.json` | **分组**：`/issues.json` `/projects.json` → **200**；`/users.json` `/time_entries.json` → **401** | ⚠️ 见下 |
| **API-84** | 越权访问（IDOR） | **P1** | 用 `<reporter1>` 对 admin 提的 Issue：① `GET /issues/<id>.json` ② `PUT` `{"issue":{"subject":"IDOR 篡改"}}` ③ `DELETE /issues/<id>.json` | ① **200**（成员可读）② **204 但回读标题未变** ③ **403** | ✅ 已拦 |
| API-85 | SQL 注入 | P1 | `POST /issues.json`，body `{"issue":{"project_id":1,"subject":"' OR '1'='1' -- "}}` | **201**（当普通字符串存）；回读 `subject` = 原文；`GET /issues.json` 仍 200（表没被 DROP） | ✅ 201 原样存储 |
| API-86 | XSS（跨站脚本） | P2 | `POST /issues.json`，body `{"issue":{"project_id":1,"subject":"<script>alert(1)</script>"}}` | **201**（原样存）；**渲染时是否转义要在界面层另测** | ✅ 原样存 |
| API-87 | 权限提升 | P1 | 用 `<reporter1>` / `<developer1>` / `<manager1>` 分别 `GET /users.json`；并用 reporter1 改他人 Issue 状态 | **403**；改他人状态返回 204 但**回读不变** | ✅ 403 |

**API-83 的完整请求（不带 Key）**

```bash
for p in /issues.json /projects.json /users.json /time_entries.json; do
  printf "%-22s %s\n" "$p" "$(curl -s -o /dev/null -w "%{http_code}" $BASE$p)"
done
```

> **⚠️ API-83 纠正了一个想当然的判断**：**不是"所有接口匿名访问都该 401"**。

| 接口 | 匿名访问 | 原因 |
|---|:---:|---|
| `/issues.json` | **200** | 匿名角色（Anonymous）默认带 `view_issues` 权限 |
| `/projects.json` | **200** | 同上，公开项目列表对匿名开放 |
| `/users.json` | **401** | 匿名角色没有 `view_users` |
| `/time_entries.json` | **401** | 匿名角色没有 `view_time_entries` |

> 这是 Redmine 的**设计意图**：公开项目的 Bug 列表允许外部查看（便于开源协作），但**用户信息和工时属于敏感数据**。
> **所以"未授权访问"这条用例的正确写法是分组断言，而不是"一律 401"** —— 按"一律 401"去测，会把 3 条正常行为误报成安全缺陷（**把"设计如此"当"漏洞"**，新手最容易犯的错）。

> **API-82 写用例时踩的坑**：第一版用 `"passwd"` 做敏感词 → 误报 —— 响应里的 `passwd_changed_on` 是「**密码最后修改时间**」，是合法普通字段。
> **检查敏感数据要精确到"密码值"，不能拿子串去撞字段名。** 改成查 `password` / `hashed_password` / `salt` / `api_key` 后通过。

> **API-85 / API-86 的正确理解**：接口返回 **201 不一定是漏洞**。"原样存储、不当代码/SQL 执行"就是正确的（Redmine 用 ORM 参数化查询）。
> **真正的注入漏洞表现是**：报数据库语法错误、或能把别的数据查出来 → 所以这两条**必须看响应体 + 回读数据**，不能只看状态码。
